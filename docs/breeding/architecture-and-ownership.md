# Breeding architecture and ownership

The executable ownership registry is `data/breeding-automation/ownership-map.json`. ADR 018 is the architectural decision; this document is the implementation map.

## Data flow

```text
app-owned reference JSON + reviewed breeding artifacts
  -> compiled species/family registry
  -> effective upstream providers
  -> authorized preview and server-issued choices
  -> durable project + consent + persisted rolls
  -> immutable Egg blueprint
  -> versioned campaign-clock incubation
  -> one atomic hatch transaction
  -> complete Pokémon sheet + Trainer link + acquisition history
  -> audience-specific Workshop projection + refresh-only realtime
```

## Fact owners

The invariant is one writer for every fact; all other integrations are readers or prohibited writers.

| Fact | Authoritative writer | Never a writer |
| --- | --- | --- |
| Canonical source facts | reviewed app-owned source migration | browser, markdown parser, `ptu-data/data` |
| Compiled species/family facts | breeding reference compiler | operation-time string parser |
| Effective Breeder permission | Edge automation | sheet label copy |
| Effective modifiers | owning provider + breeding adapter | free-form facility or client effect |
| Project | breeding project use case/repository | sheet or map repository |
| Consent | consent use case/repository | public flag, local state, note |
| Parent snapshot | project/Egg state planner | later live-parent reconciliation |
| Rolls/checks | persisted breeding roll ledger | `Math.random`, client, legacy generator |
| Egg | Pokémon Egg use case/repository | sheet, inventory, map metadata |
| Campaign time | campaign clock use case/repository | browser/process/map timer |
| Child sheet | atomic hatch use case through sheet repository | blank-create then follow-up save |
| Trainer roster link | atomic hatch use case through Trainer sheet | Egg roster or browser patch |
| Breeding origin | typed child origin written at hatch | `eggMoves`/`inheritedMoves` |
| Species acquisition | shared acquisition repository | `dexExp` inference |
| Projection | server audience projector | Vue/CSS filtering |
| Realtime | durable event log after commit | component or pre-commit publisher |

The full 22-row register, readers, prohibited writers, owner tickets, and existing/planned status are in the JSON map.

## Aggregate repositories

Planned dedicated repositories own projects, Eggs, campaign clock, operations, consent, and species acquisition. The existing sheet repository remains the only Trainer/Pokémon sheet store. Eggs do not add a sheet kind.

Repository methods accept a caller-owned SQLite connection when participating in a larger transaction. A use case, not a repository helper, owns the transaction boundary and complete read set.

## Transaction groups

### Project mutation

Project, consent effects, checks/rolls, operation result, audit event, and revision update commit together.

### Egg production

Project terminal transition, parent and provider snapshots, all offspring rolls and choices, Egg insert, operation result, and events commit together.

### Clock advancement

One clock revision, every affected project/Egg advancement, operation result, and events commit together. Duplicate advancement IDs return the stored result.

### Hatch

Egg transition, fully initialized child insert, Trainer box/team link, typed origin, acquisition history, first-species reward, operation result, and events commit together. A failure at any point rolls back every member.

## Dependency rules

- Shared contracts do not import server or Vue code.
- Pure domain code does not import routes or browser state.
- Storage does not import Vue or the map command executor.
- API routes do not issue raw SQL or interpret mechanics.
- Presentation does not import server domain code or reference JSON.
- Provider adapters consume effective projections and source hashes; they do not recreate acquisition logic.

## API and presentation

Campaign endpoints live under `/api/breeding`; Workshop routes live under `/breeding`. Responses are server-projected for exactly one audience. Normal operations have no map slug, encounter ID, placement ID, scene revision, or initiative dependency.

The Workshop may reuse Encounter design-system primitives, not Encounter authority. Its local state contains only view preferences and transient form selection that is revalidated against current server offers.

BR-070 establishes `/breeding` and `/api/breeding/workshop` as the role-projected shell. GM ownership contexts come from current campaign Trainer sheets; player contexts come only from the selected current Profile's Trainer links. The strict, self-hashed projection exposes bounded display facts and project/Egg activity booleans, never aggregate identities or private mechanics. Profile-required, no-Trainer, empty, stale-link, loading, pagination, and retry states are described in [workshop.md](workshop.md).

BR-071 adds `POST /api/breeding/projects/wizard` as a non-mutating, self-hashed presentation projection. Client values are only Profile, Trainer, and Pokémon revision selectors. The server rebuilds destination and Breeder ownership, campaign time and options, actor authority, roster links, and BR-020 parent discovery. The wizard may report same-owner or cross-owner-review-required status and the fixed campaign timeline, but it cannot create a Project, confer consent, validate private mechanics, or advance time. Final creation continues to use the existing Project setup, offer, read-set, authorization, and transaction authorities rather than a second UI authority.

BR-072 layers `POST /api/breeding/projects/wizard/guidance` over that exact current projection. Its app-owned reason catalog translates only closed BR-020 and guidance reason IDs; it does not interpret prose or recompute compatibility. Current Breeder and Dilettante status comes from the established provider handoffs, with no provider evidence crossing the projection. GM diagnostics are count/enum summaries without authority identities, while owners receive none. Cross-owner private mechanics remain unresolved until consent.

BR-073 layers `POST /api/breeding/projects/wizard/choices` over the exact guidance. Its request is selectors, a draft ID, opaque server option IDs, and explicit confirmation only. The server projects rank gates for Nature/Adept, Ability/Expert, and Gender/Master while retaining Egg production as the canonical-value checkpoint; safely labels all current campaign settings; and issues only bounded Dilettante Skill, maturity, and parent-role choices. `server/domain/breeding/currentReferences.ts` builds the operation checkpoint exclusively from the app-owned source manifest, compiled/semantic/canonical registries, current campaign options, and reviewed contracts.

A confirmed same-owner request rebuilds the complete command actor, controls, parent links/facts, provider handoffs, dependency attestations, read set, GM overrides, and BR-042 setup validation. Required review choices settle into the established immutable offer/adjudication/operation repositories before use. Creation delegates to `createBreedingProjectFromValidatedSetup`, so revision-zero Project insertion, initial campaign-clock checkpoint, operation settlement, and refresh events retain the BR-037/BR-043 transaction and replay semantics. The choice endpoint creates no parallel Project repository, roll path, timer, Egg path, or client mechanics boundary. Cross-owner confirmation stops before private mechanics and remains reserved for BR-077.

BR-074 adds `GET /api/breeding/workshop/activity` without widening the BR-070 directory. After the server reauthorizes the exact selected Trainer, it reads at most 51 owner Project and Egg rows to project the newest 50 and an explicit truncation fact. Project/Egg status, revision, progress, pause, and milestone history come only from current aggregates; consumed transfer settlements add bounded ownership-history facts. One bounded pending-operation scan supplies coarse system-recovery state. Current transfer state comes only from the Egg's transferable status/revision and durable source/recipient consents.

`shared/breeding/workshopActivity.ts` is a strict security-bound card contract; `server/domain/breeding/workshopActivity.ts` owns its pure progress/history/transfer presentation and exact self-hash; `loadBreedingWorkshopActivity.ts` owns current database/Profile/Trainer authorization and redaction. Owner cards omit a participating parent's identity, all operation/consent/Profile/evidence identities, and private provider mechanics. GM cards may identify both current parent references for the selected owner but still use bounded card facts rather than the full mechanics audit projection. The Vue component renders native progress and disclosure controls and can request an authoritative refresh; opening a transfer handoff is not a transfer mutation. The existing consent, operation, Egg, and recovery use cases remain the only durable writers.

BR-075 adds `POST /api/breeding/hatch` as a role-projected orchestration layer, not another hatch reducer. `shared/breeding/hatchWorkflow.ts` closes selector-only request and self-hashed response shapes; `server/domain/breeding/hatchWorkflow.ts` owns bounded owner/GM presentation; and `manageBreedingHatchWorkflow.ts` rebuilds current Workshop/Profile/Trainer, Egg, campaign clock/options, app-reference, and operation authority before invoking `projectPokemonEggHatchOffer`, `managePokemonEggHatchSpecial`, or `completePokemonEggHatch`. The browser can request projection, explicitly confirm begin/completion, or submit one current opaque GM special option; it cannot submit command, roll, destination facts, child facts, read sets, receipts, providers, or evidence.

The initial presentation adapter consumes the established Box offer only; BR-076 owns team/Box destination selection and navigation. Special randomness remains persisted exactly once before its reducer, and only the existing GM adjudication transaction may consume the bounded three-option offer. Completion remains the single atomic child-sheet, Trainer link, acquisition, lineage, Egg, result, and realtime transaction. The workflow projects accepted child facts only after that transaction is terminal, treats a pending durable operation as system recovery, and resolves exact retries from settled authority without redrawing, remutating, or republishing. `BreedingHatchDecisionFlow.vue` is therefore a choreography client over existing fact owners, never a storage or mechanics owner.

### Campaign-operation offer boundary

`shared/campaignOperationOffers.ts` is the source-neutral presentation contract. Breeding projects use it only through the server authority envelope in `shared/breeding/projectOffers.ts`: an owner offer is bound to current Profile control of the owner and Breeder Trainers plus effective `Breeder` Edge evidence; a GM offer is a bounded `breeding.v1` system entry point. Missing effective Breeder authority may produce only the safe unavailable reason `breeding.offer.breeder-edge-required`; malformed or stale evidence is rejected.

The projected offer carries no command payload, Profile identity, evidence hash, private parent fact, or ledger data. A client declaration echoes only the offer ID, offer definition hash, and command operation ID. Consumption rebuilds the offer from current server facts and campaign time before matching all three identities. This is an affordance boundary, not operation authorization: parent control, consent, typed GM overrides, complete read sets, mechanics, and settlement remain downstream server responsibilities.

### Breeder Edge handoff boundary

`resolveBreedingBreederEdgeHandoff.ts` is the only Edge-to-breeding bridge. It reloads the current stored Trainer and campaign clock, requires current Profile control or an exact synchronous GM verifier, resolves exactly one effective unsuppressed Trainer `Breeder` instance through Edge automation, and recomputes the mandated Skill through the server Trainer skill resolver. A direct Edge requires Novice Pokémon Education and uses its current rank and check total. A `Dilettante` grant is accepted only through the BR-061 composite resolver: the current effective Feature contribution must match the Edge acquisition source, and a server-owned command-bound choice substitutes current General Education or Perception exactly as the canonical Feature requires. It emits one self-hashed server-private bundle containing the existing BR-026 Breeder authority, an explicit Skill-application record, and its matching `edge:Breeder` dependency for `project-preview`, `project-creation`, `project-check`, or `egg-acceptance`. Submitted projections, choices, instance IDs, ranks, totals, hashes, dependencies, and delegation results have no authority.

The app-owned `Breeder` record, Edge manifest delegation, native runtime declaration, and breeding modifier inventory must all match their reviewed hashes. Edge automation owns effective identity, permission, and the contribution IDs `breeding-project-request` and `breeder-dc12-timeline`; `breeding.v1` alone owns the Project phases, campaign minutes, persisted d20, DC 12 reducer, Egg production, and hatch lifecycle. The handoff performs no mutation, roll, settlement, event, or projection. Duplicate, unresolved, suppressed, stale, malformed, asynchronous, or drifting authority fails closed. Direct acquisition below Novice fails; a Dilettante grant waives that Skill prerequisite but cannot proceed without its exact current Feature evidence and closed Skill substitution. Campaign-shared services remain unavailable.

### Feature provider handoff boundary

`resolveBreedingFeatureProviderHandoff.ts` reloads one current Trainer and the campaign clock, establishes current Profile or GM access, and resolves only effective, unsuppressed, parameter-complete Feature instances. The strict server-private handoff binds the full effective-Feature projection hash, canonical record/runtime hashes, instance provenance, one modifier-inventory contribution list, typed potential values, and one matching read-set dependency per canonical provider. `Dilettante` is active only for its selected `Breeder` grant. `Playing God` contributes bounded artificial-Egg evidence, including one of the eight canonical Species, Level 5, at most one day, choice permissions, and the current Expert-or-Master Technology Education upgrade bound. The generic converter emits self-hashed BR-046 provider-contribution snapshots; it does not itself accept an Egg or spend money/items.

The handoff records but does not prematurely execute downstream mechanics: `This One’s Special, I Know It` remains evidence-only unless an exact persisted rank-bounded use is consumed, fossil restoration and remnant-item semantics remain owned by BR-065, and `Ancient Heritage`, `Egg Tutor`, `Genetic Memory`, and `Tutoring` learning by BR-068. Feature automation retains effective identity, parameters, grants, and campaign-operation declarations; `breeding.v1` retains reducers, Projects, checks, Eggs, offspring, incubation, hatching, child construction, lineage, and outcomes. No canonical facility registry exists, so only an exact empty facility-claim array is accepted. Unknown/free-text facilities, unresolved or missing Feature parameters, suppression, source/runtime drift, stale access, provider exceptions, and Promise-like callbacks fail before any mutation, roll, event, or projection.

### Parent discovery boundary

Parent discovery reads only current Trainer `currentTeam` and `boxedPokemon` links after actor, Profile, and selected-Trainer authorization. Public sheet flags, legacy grants, and map placement do not expand discovery. Players receive candidates from one currently controlled Trainer; an authenticated GM may query bounded campaign Trainer rows without adopting a Profile. Duplicate ownership links fail closed, and a missing linked Pokémon becomes an unavailable candidate with no inferred facts.

Filters run after authorization. Selection binds zero to two visible Pokémon slugs and exact revisions; hidden, filtered, missing, or stale selections share one non-enumerating failure. A selected pair receives only a deterministic safe compatibility preview. Even a structurally plausible pair is labelled `requires-validation`: current ownership, revisions, maturity, consent, facility/location policy, and final compatibility still belong to the operation read set and authorization path.

### Project setup validation boundary

`server/domain/breeding/projectSetupValidation.ts` composes the BR-026 authorization receipt with current parent facts, maturity policy, the closed Workshop location policy, and the pure compatibility evaluator. Evaluation is staged: an unauthorized request, an awaiting-consent cross-owner creation, or an unsupported facility returns before private parent mechanics may be loaded. Cross-owner previews remain unavailable; creation may establish only an `awaiting-parent-consent` project, while later project operations must revalidate the positive, revision-bound consent evidence defined by BR-026.

Authorized evaluation binds both command-ordered parents to exact sheet/control/read-set revisions and compiled Species-spec hashes. The default maturity policy accepts only two resolved positive GM confirmations whose persisted settlement command, complete read set, authenticated GM receipt, and terminal result are rechecked by a server dependency. Minimum-Level campaigns use only the bound option snapshot. Same-sex parent-role intervention consumes one matching bounded offer strictly before campaign-minute expiry; free-text outcomes and extraneous adjudications are rejected.

The only accepted location policy is `campaign-workshop-off-map-v1`. The reviewed provider inventory currently contains zero facility definitions, so any facility dependency fails closed rather than conferring a bonus. Map, encounter, placement, scene, and initiative state are never location evidence. Owner and GM projections contain only bounded statuses, reasons, compatibility kind, and the closed location/facility result; identities, hashes, controls, consent, offers, adjudications, and parent facts remain server-private.

### Initial project progress boundary

A ready BR-042 setup creates revision 0 in `initial-time-in-progress` at the exact current campaign-clock checkpoint. An awaiting-consent setup creates revision 0 without a start or clock checkpoint. Initial work requires 240 cumulative campaign minutes; neither process time nor map, encounter, scene, initiative, or browser time can accrue it. Each advancement binds the full command, current Project revision and document hash, current campaign-clock revision/minute, command-ordered parent revisions, complete read set, segment dependency, and authorization receipt.

Interruption credits only the valid prefix since the prior durable checkpoint, preserves all credited minutes, records the through-checkpoint without crediting paused time, and moves the Project to `awaiting-parent-consent`. Resume starts at a fresh campaign-clock checkpoint, so time spent paused cannot be recovered implicitly. Parent revisions may move forward only in an interruption segment; accrual under drift or any backward revision fails closed. Crossing 240 minutes records the exact threshold minute even when the operation observes a later clock minute.

`manageBreedingProjectInitialTime.ts` persists the immutable read-set/authorization pair, Project CAS transition, terminal operation result, and bounded audience refresh rows in the BR-037 phase-2 transaction. Failure retains only the phase-1 pending reservation; explicit recovery must use the exact command and authority. Terminal exact retry performs no accrual, Project revision, event insertion, or publication. Owner and GM progress projections disclose only status, required/credited/remaining minutes, interruption state, and readiness minute—not aggregate IDs, parent/Trainer/Profile identities, consent, commands, read sets, hashes, or provider evidence.

### Breeder check boundary

A `check-ready` Project permits one command-bound Breeder DC 12 check. Direct Edge authority uses Pokémon Education; a Dilettante grant uses its hash-bound current General Education or Perception application. The authoritative Skill identity and total come only from the exact current effective `Breeder` evidence for the Project's Breeder Trainer, bound to its Trainer revision, Edge/Feature projection, read-set dependency, authorization receipt, ruleset, and campaign minute. Editable labels or client choices/totals never contribute. Both parent revisions remain in the read set; every cross-owner parent also requires current positive consent and operation-bound consent evidence. A GM override is not consent.

The operation is durably reserved before randomness. One server d20 is then assigned a deterministic operation-local roll identity and committed with the immutable read set and authorization receipt before the reducer runs. The reducer reloads that roll, adds the frozen authoritative skill total, and succeeds exactly at final total 12 or higher. Clear stale, unavailable, or missing-consent states draw nothing. If phase 2 fails, the pending operation and its one roll survive; explicit recovery reuses that roll and never draws again.

On success the Project records the check and atomically enters `additional-time-in-progress` with zero additional minutes at the current clock checkpoint. Failure records the same immutable check and enters terminal `check-failed`. Project CAS, check row, terminal operation result, and bounded refresh events commit together. The owner/GM projection exposes only outcome, DC, final total, and campaign resolution minute; it omits the die, skill component, identities, commands, read sets, hashes, and consent/provider evidence.

### Additional-time completion boundary

Only a Project that retains its exact successful persisted check may accrue the additional 240 campaign minutes. Each command binds the current Project document, check row, campaign-clock checkpoint, both immutable parent revisions, reference snapshot, and a self-hashed server segment authority into one complete read set and authorized receipt. Parent drift after the check is stale authority. Cross-owner parents require current positive operation-bound consent, consumed strictly before expiry; a GM override never substitutes for consent.

The segment's `creditedFromCampaignMinute` is server-derived. For same-owner Projects it equals the last durable checkpoint. For cross-owner Projects it is the maximum of that checkpoint and every current consent's durable grant minute. This permits a fresh grant to resume work without crediting an unauthorised gap. The Project's clock checkpoint advances through the command minute, while only the bounded interval from `creditedFromCampaignMinute` earns progress. Cumulative progress never decreases or exceeds 240. Overshoot transitions to `ready-to-produce` and records the exact minute the cumulative threshold was reached, not the later command minute.

`advanceBreedingProjectAdditionalTime.ts` commits immutable operation evidence, the Project CAS, terminal result, and bounded refresh rows in one coordinator transaction. Phase-2 failure leaves only the recoverable pending reservation. Explicit recovery reuses the exact authority; terminal retry cannot reaccrue or republish. Owner/GM projections expose only status, required/accumulated/remaining additional minutes, and readiness minute. Check/roll components, aggregate and actor identities, consent, commands, read sets, and hashes remain private.

### Egg-acceptance snapshot boundary

A `ready-to-produce` Project can construct one strict Egg-acceptance snapshot package for its `produce-egg` command. The package freezes the exact successful check, ordered parent snapshots, current Breeder snapshot, typed effective-provider values, complete app-reference snapshot, and all 15 campaign-option values. It binds those facts to the current Project revision/document hash, command hash, complete read set, authorized receipt, campaign minute, ruleset, compiled registry, and security policy. The package is deeply immutable and self-hashed at every nested boundary.

Parent snapshots must retain the Project's sheet identities, owners, and post-check immutable revisions; current source-sheet hashes; canonical species/family/spec/Egg Group facts; bounded role and maturity evidence; complete effective-known-Move provenance; and current control or cross-owner consent. A changed parent revision, manufactured Move source, expired consent, or GM override used as consent fails closed. The current effective Breeder authority supplies the exact Trainer revision, rank, Edge instance/record/projection, and provider snapshot binding. Editable labels and submitted ranks have no authority.

Provider values use a closed typed union and only reviewed contribution IDs from `modifier-inventory.json`. Every contribution matches one exact effective dependency and receipt hash. A separate system dependency attests the complete provider-snapshot hash, preventing silent omission. Unknown contributions, free-text patches, client effects, and unregistered facilities are rejected. The complete reference snapshot must match every app-owned source hash and current compiled artifacts; the full option snapshot must match the Project's creation hash.

The BR-046 package is not an independent precommit aggregate and has no browser authority. It becomes durable authority only when BR-048 commits it with the accepted Egg in the same transaction; no in-memory preview may claim acceptance. Egg definition hashes are the exact sorted closure of the frozen Project, check, parent/spec/Move, Breeder, provider, reference, registry, ruleset, and option definitions. Owner/GM projection exposes only frozen status, checkpoint, campaign minute, and fixed snapshot-kind labels.

### Offspring-production resolution boundary

`server/domain/breeding/offspringProduction.ts` reduces only an exact `produce-egg` command, its authoritative BR-046 snapshot, persisted operation rolls, and current server-issued offers. The command's requested roll kinds map to a closed purpose sequence. Roll rows are operation/command/Project-revision/campaign-minute bound, gap-free from ordinal zero, and retain the exact snapshot, ruleset, offspring, trait, Nature, canonical-ID, and compiled-registry hash closure. The Ability uniform-index die has exactly as many sides as the offspring Species' sorted Basic Ability inventory. Missing, extra, reordered, stale, biased, or enriched rows fail before a result can be accepted.

Family and Species resolution reuses the reviewed Ditto, core d20, maternal, and bounded-GM policies. Nature, Ability, and Gender are either their required persisted random result or one current bounded rank-authorized choice—never both. Choice options come from immutable revision-zero offers targeted to the exact Project revision and actor Profile. They expire at equality. A selected option must be unique, canonical, and permitted by the frozen Pokémon Education rank. The planner produces one revision-one `consumed` successor bound to the settlement operation, command hash, and campaign minute; BR-048 applies that successor only in the Egg transaction.

Inheritance is rebuilt from the frozen effective-known-Move snapshots. Every candidate retains parent index/reference/Species, the compiled child Egg-Move or machine-compatible pathway, and the complete known-Move evidence. Breeding production cannot substitute parentless source authority. The immutable offspring blueprint also freezes the canonical Species/Family root/spec hash, trait provenance, starting Level, and either a disabled or policy-bound Baby Template result. Ordinary optional-template offers are issued only by the server from the exact Project revision and frozen campaign-option snapshot; their decline/application values carry the reviewed BR-067 evidence ID and policy-bound value hashes. Provider contributions remain unavailable until their reviewed source-specific reducers exist; BR-061 Feature evidence cannot become a free-form effect.

The strict resolution record cross-checks every nested hash, roll reference, bounded option, canonical authority, inheritance source, and source-evidence hash. It is phase-2 planning evidence, not a second aggregate: only the BR-048 transaction may make it authoritative by inserting the Egg, applying offer successors, linking the durable rolls, and terminally settling the Project operation together. Its owner/GM projection discloses only prepared status, campaign minute, and two completion booleans.

### Atomic Egg-production boundary

`produceBreedingProjectEgg.ts` reserves the exact `produce-egg` command before randomness and persists the immutable read-set/authorization pair. Each complete server roll is then committed in its own caller-owned transaction before that reducer runs. A later random-source failure leaves earlier operation-bound rolls durable; explicit recovery draws only the first missing declared roll. A terminal retry never enters preparation or publication.

Phase 2 rebuilds BR-046 from the current `ready-to-produce` Project, successful check, campaign clock, parent and Breeder sheet revisions, consent records, selected offers, references, and provider facts. It reloads only persisted rolls for BR-047. One BR-037 transaction applies selected-offer successors, inserts revision-zero `PokemonEggDocument v1`, advances the Project exactly once to `egg-produced`, settles the operation, and appends refresh rows. Any planner, CAS, insert, offer, event, or settlement failure rolls all phase-2 effects back while retaining the recoverable reservation, evidence, and rolls.

The Egg is a dedicated `incubating` aggregate owned by the Project owner Trainer. It stores the breeding source Project, frozen ruleset, BR-046 parents and Breeder, BR-047 offspring blueprint, and the strict sorted definition-hash closure. Incubation starts at zero at the exact campaign-clock checkpoint; fixed-average duration is the only BR-048 production mode. BR-050 validates the frozen target and bounded variation authority, while provider-specific duration or rate contributions remain gated on their owning source reducer. Special state starts `not-rolled`, `automaticShiny` remains false, and no child sheet exists. The Project successor records the same Egg ID and production campaign minute while retaining immutable parents, check, owner, Breeder, and ruleset.

Cross-owner consent is loaded again inside phase 2 and must remain positive and strictly unexpired. Offer consumption is never an earlier side effect. Project refreshes may target the participating owner; Egg refreshes structurally forbid that audience and target only diagnostic, GM, owner, and public access. All rows publish after commit. The mutation projection exposes only Egg/Project revisions, production campaign minute, and coarse source/incubation status; private traits, inheritance, identities, rolls, offers, consent, commands, and hashes require a later authorized aggregate projection.

### Authoritative incubation boundary

`managePokemonEggIncubation.ts` advances only from the Egg's durable campaign-clock checkpoint through the exact current clock revision and minute in a complete read set. At base rate, one valid campaign minute earns one incubation minute. Progress is cumulative and clamped to the frozen target; any excess is retained only in the immutable operation segment. Reaching the target atomically records `incubation-complete`, the exact threshold campaign minute, the ready operation, and the `ready` Egg successor. Transfers, storage, or loss of a parent, Breeder, or production source do not implicitly interrupt this clock.

Pause and resume are explicit `set-egg-incubation-pause` operations. Pausing credits the valid unpaused prefix before its checkpoint. A paused interval is wholly skipped, and resuming first preserves that skipped interval before establishing a durable restart checkpoint. An owner may use only the owner-request reason while currently controlling the Egg owner Trainer; GM control needs one command-bound owner-control override and one closed reason. A pause request cannot conceal a threshold already reached: readiness must settle through the ordinary advance reducer.

Every accepted mutation inserts one self-hashed `breeding_incubation_segments` row keyed by the operation and exact Egg revision transition. Phase 1 atomically reserves the command with its complete read set and authorization receipt so a pending pause cannot be rebound to a later clock. One BR-037 phase-2 transaction then commits the Egg successor, segment, terminal result, and four bounded refresh rows. Failure retains the recoverable pending reservation and immutable authority evidence; exact retry or restart recovery reuses them without another Egg revision or publication. Complete campaign backups include and cross-link these segment rows. Owner-portable archives do not.

BR-050's executable modifier mode is deliberately `base-rate-only`. The shared continuous-contribution envelope is bounded, canonical, revision-bound, and self-hashed, but parsing it does not authorize its effect. Any non-empty contribution fails closed until its owning source-specific reducer supplies current read-set evidence and integration policy. The reserved policies are continuous 2× progress for the Egg Warmer item and one command-bound `1d10` reduction for the Egg Warmer capability (1 grants no reduction; 2–10 grant result × 60 campaign minutes). Unknown facilities remain unavailable because no app-owned canonical facility registry exists.

`queryPokemonEggIncubation` returns only an owner or GM projection after current authority succeeds. It exposes the Egg ID/revision, coarse status, totals, basis points, pause/readiness state, durable clock checkpoint, and allowed actions. It never projects offspring traits, parent or Breeder identity, Profiles, consent, providers, rolls, offers, command/evidence payloads, or hashes. Participating-owner access is structurally absent.

### GM readiness-correction boundary

`markPokemonEggReady.ts` is the only manual readiness path. An authenticated GM must submit `mark-egg-ready` with one closed correction reason and one command-bound `operation-recovery` override targeted to that same operation. The complete read set binds the current incubating Egg, current campaign clock, one `breeding-egg-readiness-correction-v1` policy dependency, and the resolver attestation. Owner control, client declarations, free text, and direct field edits cannot grant this authority.

The reducer advances the Egg exactly once from unpaused `incubating` to `ready`, records `gm-mark-ready` and the current campaign minute, and preserves the immutable target, accumulated progress, and last applied clock checkpoint. It does not fabricate elapsed time, overflow, or an incubation segment. A paused Egg must first resume through its own audited operation; an already-ready Egg cannot be corrected again or moved back to incubating.

Phase 1 durably binds the pending command to its exact read set and authorization receipt. One BR-037 phase-2 transaction commits the Egg successor, accepted `egg-ready` result, and four bounded refresh rows. Rollback retains only recoverable phase-one evidence, and exact retry cannot create another revision or publication. Campaign-backup integrity requires the Egg's ready-operation link to resolve to the accepted typed command, reason, campaign minute, and Egg revision result.

The GM-only correction projection exposes only operation/Egg identity, accepted and current revision, coarse status, typed reason, target/accumulated totals, and correction minute. Owners can observe the generic `gm-mark-ready` readiness kind through their ordinary incubation projection but not the correction reason, override, command, receipt, or hashes. `mark-egg-ready` appears as an available action only in a current GM projection for an unpaused incubating Egg.

### Campaign-clock incubation batch boundary

`advanceBreedingCampaignClockBatch.ts` integrates campaign-clock advancement with bounded Egg catch-up. Before reservation, the server discovers the first 100 `incubating` Eggs whose durable clock checkpoint is behind the requested target, in canonical Egg-ID order. The parent `advance-campaign-clock` command must declare the current clock followed by exactly that page and every current Egg revision. Omitted, reordered, stale, enriched, Project, or client-selected scopes fail before time changes.

The parent requires current authenticated GM authority, one self-targeted recovery override, a complete clock/Egg read set, current app reference versions, one batch-policy dependency, and the resolver attestation. It durably reserves that evidence before the clock CAS. Every Egg scope then derives a stable namespaced child operation, read-set, and override identity from the parent operation and Egg ID. The child runs the ordinary BR-050 base-rate reducer at the parent clock result, so long downtime receives the same exact threshold, overflow, pause-skip, modifier, and privacy rules as an individual advance.

The parent clock and each child Egg are intentionally separate top-level transactions; the coordinator is never nested.
