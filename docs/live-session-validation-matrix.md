# Live session validation matrix

This matrix maps the live-session implementation areas to the validation expected before each area is considered ready. It serves as a product/developer review index for the current implementation areas.

Live session remains locked to the GM-hosted session architecture described in the [Live session roadmap](live-session-roadmap.md), [glossary](live-session-glossary.md), and ADRs. The matrix should be updated only to clarify validation expectations, not to replace the architecture with a SaaS, generic shared-document editor, cloud-database, or Quick Tunnel-first model.

## Baseline for every live-session change

Every live-session change should include the narrowest useful validation for the behaviour it introduces:

- Run the standard checks: `npm run typecheck`, `npm test`, and `npm run build` before review.
- Add focused Vitest coverage for pure logic, route/use-case behaviour, message schema handling, command validation, permissions, conflicts, reconnect, or persistence when those behaviours change.
- Add manual smoke notes or runbook steps when the behaviour depends on multiple browsers, LAN devices, named tunnels, or browser WebSocket behaviour that unit tests cannot fully cover.
- Update target documentation when setup, architecture, protocol, operations, security, recovery, limitations, or user-visible session behaviour changes.
- Preserve local mode, legacy non-session paths, private data boundaries, and map rendering quality unless a reviewed change explicitly and safely updates them.
- Keep examples free of real secrets, private maps, generated sheets, session snapshots, event logs, tunnel credentials, or real `.env` files.

## Cross-cutting validation checklist

Use this checklist when reviewing any live-session implementation area:

- **Architecture lock:** The change keeps the product as a GM-hosted table session, not SaaS, public multi-tenancy, a generic collaborative document editor, or a cloud-first rewrite.
- **Runtime gate:** Session hosting remains disabled by default and fails closed unless the documented session-host flag is enabled.
- **Server authority:** Live session state changes go through validated server-authoritative commands, not live-client whole-map autosave.
- **Revisions and idempotency:** Accepted commands advance monotonic revisions exactly once; duplicate `opId` retries are idempotent; rejections do not advance revisions.
- **Permissions:** Players can affect only assigned and visible resources, while GM actions still pass validation and safety checks.
- **Reconnect:** Clients recover from server state through replay or snapshot fallback instead of trusting stale optimistic edits.
- **Persistence:** Session snapshots and optional event logs are local JSON files with atomic-write and backup/recovery expectations; no Postgres, Redis, Durable Objects, or hosted database is introduced.
- **Transport:** New session concurrency uses WebSockets for commands, acks/rejections, broadcasts, presence, heartbeat, and reconnect; legacy SSE may remain only for non-session/local paths during migration.
- **Hosting:** LAN is the primary supported path and named Cloudflare Tunnel is the supported remote path; Quick Tunnel is development smoke-test only.
- **Data hygiene:** Private campaign data, generated sheets, snapshots, event logs, secrets, tunnel tokens, private keys, and real `.env` files stay out of git.
- **No map rendering performance regression:** Existing local-first map/sheet workflows and render quality remain intact unless a reviewed follow-up explicitly documents and validates a safe change.
