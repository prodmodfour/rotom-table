# Live play authority

This document defines Rotom Table's normal multiplayer system: server-authoritative profile play on regular `/maps/<slug>` routes. This is normal profile play. The legacy `/sessions` surface is maintenance-only while it remains in the codebase.

## Non-negotiable authority boundary

SQLite is the only runtime authority for maps, Pokémon sheets, trainer sheets, group inventories, shop tables, map folders, sheet folders, shared map interaction mode, map live-play operation results, shop checkout operation results, and durable realtime replay events.

Normal API requests must not read runtime maps, sheets, group inventories, or shop tables from `data/maps`, `data/sheets`, `data/trainers`, `data/group-inventories`, or `data/shops`, and normal mutations must not write authoritative map/sheet/group-inventory/shop JSON. JSON map/sheet/group-inventory/shop files are limited to explicit migration/import where supported, explicit export/interchange, operator backup material, or clearly labeled generation output. Encounter spawn generates Pokémon sheets in memory, then persists the generated sheets and map placements to SQLite in one transaction.

Browser-owned whole-map autosave is never the authority for live gameplay. During live play, clients send explicit commands. The server accepts or rejects those commands after validating actor, profile, visibility, token/sheet control, command shape, `baseRevision`, and conflict scope.

## Mode split

### Prepare Map / setup-edit

Setup/edit mode is GM/operator preparation and maintenance. Whole-document map and sheet saves write SQLite documents and require an `expectedRevision`; stale saves reject. The map save route requires GM role, explicit `interactionMode: "setup-edit"`, and the shared map mode to be **Prepare Map**.

### Run Live Play

Live play uses persistent player profiles and normal map URLs. Gameplay mutations are commands such as move token, turn token, modify HP/conditions/combat stages, resolve a move, use a move/ability/order/manoeuvre, send out, capture, advance initiative, place hazards, edit terrain, spawn/delete tokens, and update sheet-backed combat state. Command routes reject while the map is in **Prepare Map**.

### Shared group inventory

The `/group-inventory` page is campaign-level inventory state, not map metadata and not a hidden trainer sheet. GM direct edits use revision-checked full-document saves. GM and player trainer transfers use atomic page-level APIs that validate both group inventory and trainer sheet revisions; player transfers are limited to trainer sheets linked to the selected player profile. A future `groupInventory` live-play command scope should be added only if in-map item consumption or another gameplay command needs to mutate party inventory. See [Group inventory workflow](group-inventory.md) for the current workflow and future command boundary.

## Atomic command and batch workflows

Every accepted persistent command or batch workflow uses one synchronous SQLite transaction for all affected documents, live-operation results, and durable realtime rows. Expected map/sheet revisions are checked before writing. Complete changed documents are written once. Durable event rows are appended before commit. Exact sequenced events are published only after commit, so rollback cannot produce a success publication.

This applies to:

- live move resolution, capture, send out, ability/order/manoeuvre, move usage, HP/condition/combat-stage changes, initiative, terrain, hazards, field effects, scene, start-turn modal, token spawn/delete/move/turn, and attack of opportunity commands;
- sheet rename/delete with map placement retargeting or cleanup;
- encounter spawn;
- campaign next-day processing;
- setup map and sheet saves;
- map/sheet library and folder mutations;
- shared map interaction-mode changes;
- group inventory GM saves and trainer transfers;
- accepted shop checkout commands that update shop stock plus trainer sheet or group inventory money/inventory.

Authoritative `resolveMove` planning also records a deduplicated `sheetReads` snapshot for the acting sheet, every consulted selected or area-candidate target sheet, and indirect rule providers such as condition-immunity auras. Each entry carries sheet kind, slug, and observed revision; conflicting observations of the same sheet reference reject planning. This collection is server-internal and cannot be supplied by the client. Before any map or sheet write, the accepted-result transaction asserts every recorded sheet revision, including read-only misses, immune targets, and aura providers. A stale or missing consulted sheet rejects the move as a conflict without writing the map, sheets, operation result, or realtime rows; read-only sheets are never no-op written merely to obtain CAS protection.

Successful move planning produces a bounded structured audit trace tied to the reviewed runtime definition hash and frozen rules-source hash. It records canonical phase transitions, predicate decisions, target inclusion/exclusion, server rolls, operation inputs/results, prevented effects, choices, and child ancestry. The durable accepted result carries a sanitized projection: raw operation/predicate data, selected option IDs, and predicate-excluded target identities and event counts remain server-only; size-bounded public summaries retain their public event count. Historical stored results from before this field remain readable. Clients cannot submit either trace form. Deterministic trace lines can be rendered for diagnostics without treating legacy prose log lines as the only audit evidence.

Reviewed MoveSpec v2 definitions enter a pure phased interpreter boundary before any planner or repository. The executor revalidates definition integrity and ruleset provenance, walks only canonical phases, resolves server-owned selectors and supported predicates, records injected rolls, and emits typed operations without mutating maps or sheets. An unresolved choice or reaction stops at that exact phase and partitions accumulated work: only a direct-HP declaration cost explicitly reviewed in the `pay` phase can enter the pre-window typed plan, while ordinary damage, effects, rolls, and logs remain in the deferred continuation. A pure materializer derives both the strict private pending candidate and its bounded public summary from the same trace, ledger, read set, runtime identity, and response request; an implicit pre-window mutation fails closed. Capability families that do not yet have interpreter or reducer semantics fail closed rather than being ignored; persistence remains a separate planning and commit concern.

The shared pending-resolution contract strictly bounds and cross-checks the continuation kind, suspended identity, originating map and operation, reviewed definition/ruleset hashes, current phase, complete revisioned resource read set, audit trace, roll ledger, outstanding response windows, accepted option history, causal ancestry, timestamps, and privacy-safe map summary. Pre-existing rows without a continuation kind normalize to `movespec-v2`; reviewed accepted-move ability follow-ups use the separate `ability-follow-ups` continuation, and current durable opportunity-attack responses use `attack-of-opportunity`. A response window stores only stable IDs, presentation lookup keys, resolved ownership, pass policy, and bounded server priority—never callbacks, effect programs, rolls, or arbitrary patches. Reaction windows additionally retain their canonical timing and server-derived causal depth. Their checkpoints are `declare`, `pre-cost`, `target`, `pre-hit`, `post-hit`, `pre-damage`, `post-damage`, `ko`, `movement-step`, `switch`, and `cleanup`; each maps to one executable MoveSpec phase. Reactions at one checkpoint execute by descending priority, then stable reviewed operation ID, independently of component or provider iteration order. Passing declines and closes only the current window, spends no reaction resource, and resumes at the next priority; the same checkpoint reopens only for a new causal fact. Nested child windows are bounded to depth eight. Each checkpoint defines the maximum already-authoritative information class an eligible responder may receive (for example, pre-hit excludes hit outcomes and pre-damage excludes final damage); this timing table never bypasses normal authorization, hidden-target, roll, or sheet-value redaction. Event-backed post-fact checkpoints bind only to authoritative move, movement, switch, and cleanup lifecycle facts, while pre-fact checkpoints come directly from the interpreter. Its lifecycle distinguishes `pending` and `resuming` from the terminal `committed`, `cancelled`, `expired`, `conflicted`, and `abandoned` states. Canonical private records persist in the dedicated `pending_move_resolutions` SQLite table under a unique resolution ID and originating map/operation pair, with CAS revision metadata and an optional explicit link to a terminal `live_play_ops` row. Pending rows are not terminal operation results, and encounter state carries only bounded public summaries/IDs.

Authorized choose, react, and pass commands now resume this durable state. The server resolves submitted IDs against the current private window, reproduces the stored trace/roll prefix with replayed server draws, excludes declaration costs that already committed, and validates the complete map/sheet read set before any continuation write. One transaction records the chosen option and either replaces the public summary with the next window or commits the final typed map/sheet plan, terminal operation result, pending-record status/link, and durable realtime rows. A stale consulted resource terminally conflicts the saga and removes its public summary without applying deferred effects. Exact response-command replay uses the stored operation hash/result and never re-enters the interpreter. Selected option IDs remain in private audit state and are omitted from accepted wire trace summaries.

Shield-family canary machinery uses reviewed server definitions and a bounded pre-commit provoking-plan projection. Self, explicit-side, and authoritative-area coverage are derived from placement identity, side relationships, and server-produced scope candidates; unknown allegiance fails closed for side protection. A selected guard removes protected hit identities and every corresponding planned effect before persistence, records typed prevention evidence, emits only reviewed melee retaliation operations, and appends one shield-owned usage spend. A reviewed higher-priority Feint break leaves the provoking plan intact but still records the shield use, while exact response-operation replay appends neither usage nor retaliation again. These definitions cover Protect, Detect, Baneful Bunker, King’s Shield, Obstruct, Spiky Shield, Crafty Shield, Mat Block, Quick Guard, and Wide Guard as engine canaries only; their production move registrations and semantic status changes remain assigned to the Phase 9 cohorts.

Counter-family canary machinery consumes only strict authoritative `move-damaged` facts. Counter and Mirror Coat retain the triggering class/type, aggregate deduplicated post-prevention HP plus temporary-HP loss, record their one-step resistance adjustment, and emit an ancestry-linked typed direct-HP response only when the reactor remains conscious and the response type is not immune. Bide stores those same event-identified effective-loss records in a bounded immutable continuation, accepts each later damaging-move event once, and releases the total only on its scheduled next available turn to server-classified adjacent enemies. Magic Coat redirects the affected typed status/effect recipients back to the provoking user with the reflector as source; Snatch redirects only reviewed benefit operations while leaving costs on the original user. Every response has one triggering-parent/reaction-child link, usage identity, and replay key, so duplicate delivery cannot count a damage fact, spend usage, release Bide, or redirect an effect twice. Counter, Mirror Coat, Bide, Magic Coat, and Snatch remain engine canaries here; Phase 9 owns production registration and semantic promotion.

Setup/redirection canary machinery keeps declare-now mechanics in a bounded immutable pre-commit plan. Focus Punch drops its deferred attack and frequency spend when one authoritative damage fact reaches the reviewed quarter-maximum-HP threshold; Beak Blast and Shell Trap consume server-classified melee `move-hit` facts for typed Burn work or a durable child window. Round-end execution exposes the original deferred plan only after its setup marker becomes ready. Follow Me and Rage Powder start from geometry-produced recipients, fail unknown allegiance closed, and replace every resolved target recipient before accuracy; Rage Powder also records its required shift toward the source. Feint and Drown Out remove shield or Sonic mechanics from the provoking plan while retaining reviewed triggering usage, rather than applying an inverse after commit. Pursuit and Shell Trap child plans explicitly replace source/target identities and spend once under replay. Source turn-end, KO, recall, switch, and scene facts expire the relevant setup/redirection state. These Focus Punch, Beak Blast, Shell Trap, Follow Me, Rage Powder, Feint, Pursuit, and Chatter/Drown Out definitions are engine canaries only; later cohorts own production registration and semantic promotion.

Pending termination is likewise authoritative and atomic. New pending rows persist the exact typed declaration-time plan separately from the private resolution JSON. GM cancellation removes the public summary and inverts only declaration-owned values after current-value checks and per-resource CAS; it never restores a whole resource snapshot. If a safe inverse is unavailable, the explicit authorized abandonment recovery path terminates without rewriting the retained cost. GM force-resolve is a server-authorized force-pass, including for a reviewed window that does not normally permit pass. Scene end expires unresolved moves from the authoritative `scene-end` encounter event in the same transaction as scene cleanup and declaration compensation; elapsed wall-clock time never advances this rule. Cancellation, abandonment, and expiry append a bounded terminal audit operation, clear all response windows, and leave a terminal record that cannot be resumed.

A native MoveSpec declaration that reaches an unresolved window now commits that private pending row and its map summary in one SQLite transaction. The map and every consulted sheet revision are checked under the transaction; no damage or ordinary effect emitted before the window is applied. Only an explicit typed direct-HP cost in the `pay` phase with declaration timing and reviewed resource-cost declarations whose phases have been reached may commit before suspension; those writes join the same transaction with matching command conflict scopes. Immediately before writing, the persistence boundary re-derives the exact allowed map and sheet envelope from the materialized pre-window plan and rejects any divergent planner output. The transaction is committed before the pending acknowledgement returns, so no SQLite transaction or write lock remains open while a participant decides. The HTTP acknowledgement is marked `pending: true`, carries only the public summary, and is deliberately excluded from terminal operation-result storage and accepted-move presentation. Its deterministic resolution identity is derived from the canonical declaration command hash, so an exact duplicate returns the same durable prompt without replanning, rerolling, or spending again, while changed command material under the same `opId` conflicts. Interpreter requests addressed to the acting placement materialize as actor-owned windows; non-actor authoritative recipients materialize as target-owned windows, so a defender's reaction belongs to the defender rather than to the attacker.

Durable response intent has five strict ID-only wire commands: choose, react, pass, GM cancel, and GM force-resolve (force-pass). Each carries the live-play `opId`, map slug and base revision, an optional selected profile authorization ID, plus only the relevant resolution, window, and option IDs. Exact-field parsing rejects scopes, rolls, effects, patches, scripts, state, coordinates, directions, paths, distances, movement modes, occupancy policies, and any other client-authored mechanics. Before a response use case can run, the server resolves those IDs against the current private pending record and rejects missing or inactive resolutions, reused response/window identities, wrong window kinds, disallowed passes, cross-map references, and unknown options. Window ownership may name the actor, a target or concrete placement, a selected profile, a side, or GM authority. Player matches are derived from the current selected profile, linked trainer roster, map placements, and explicit side IDs; controlling the attacker does not grant control of a target-owned reaction. Authorized GMs can supervise every current window. Authorization runs before an option ID is exposed to the execution seam.

Authenticated viewers can query `GET /api/maps/move-responses/pending?slug=<map>&profileId=<profile>` for their currently eligible windows. The response includes only the public resolution summary and presentation-safe window fields/options. It never includes ownership principals, operation IDs, target identities, read sets, roll ledgers, or audit traces; ineligible windows are omitted, and hidden maps reject before the private pending repository is listed. Choose/react/pass routes require an authenticated table role and a matching selected profile for players; cancel and force-resolve require GM role; every mutation route remains behind the hosted-write guard. All five mutation routes execute through the contextual parser, ownership policy, durable operation idempotency, and transactional continuation or termination use case.

The live map renders those authorized windows in a generic durable-response panel. It derives actor and responder labels only from the viewer's already-visible map/profile context, treats prompt and option keys as presentation text only, and submits the server-issued resolution/window/option IDs without deriving mechanics from their labels. Typed movement options may additionally project their server-issued destination/direction onto the battlefield as selectable markers; clicking one still sends only its opaque option ID, never a coordinate or path. Every choose, react, pass, cancel, or force-pass body is written exactly to the IndexedDB command journal before transport. The panel distinguishes pending, sending, and uncertain delivery; an uncertain retry reuses the exact journaled body and `opId`. Refresh, profile changes, and authoritative map revision changes refetch eligible windows, while one browser instance processes a terminal response operation at most once before adopting its authoritative map/sheet documents.

Encounter-state effect instances are bounded discriminated data for condition, numeric-modifier, and capability payloads. A temporary-effect operation may request only the context-free typed definition; authoritative reducer context—not the spec—must supply source operation/move/placement identity, affected placements/sides/cells, creation turn/round, and suppression state. Each instance carries explicit source/target turn, round, scene, triggered, or permanent duration policy plus replace/refresh/add-stack/independent reapplication and bounded charge-consumption policy. The server-only policy transition is pure: one effect collection plus one authoritative lifecycle fact always yields the same ordered effects and transition evidence, including removal of dangling suppression sources. The shared encounter-event contract defines exact bounded facts for scene/round/turn boundaries, move outcomes, movement, switching, effects, and encounter resources. Every fact names its source operation and optional causal parent; strict parsing rejects unknown fields, executable values, arbitrary payloads, and state patches. These events are server-internal reducer inputs, not client-authored commands. The pure lifecycle reducer consumes one ordered root batch, applies effect add/remove and timing transitions, lets ordered server-only trigger handlers enqueue only shared typed operations, consumes exact active-effect charges, updates structured encounter history, and recursively reduces strictly causal child events depth-first. It returns immutable state, operation and transition queues, bounded execution counters, and ordered trace evidence; duplicate identity, invalid provenance, suppression, recursion, emission, operation, trigger, history, and trace violations fail closed.

Generalized battlefield zones are a separate bounded discriminated collection for battlefield-, cell-, placement-, or side-scoped rules. Every zone has one durable identity, accepted-operation or deterministic legacy source, explicit side ownership, layer, duration, stacking policy, typed entry/exit handler references, and typed targeting/damage/movement modifier lists. Battlefield-wide Weather, Terrain, and Room fields additionally retain a bounded server-owned priority, stable replacement group, and exact suppressing-zone references. One priority decision owns replacement: equal priority accepts the latest authoritative application, lower priority is prevented, and suppression retains the instance without contributing mechanics. A delayed Room is likewise inactive until its authoritative next-round activation. Layered hazard and pledge payloads additionally retain a stable family plus bounded current/maximum charges. Its closed payload families cover hazards, Weather, Terrain, Rooms, smoke, barriers, pledges, vortexes, and side conditions; no zone accepts prose, arbitrary metadata, callbacks, or client-authored effect operations. The server query seam matches complete placement footprints and explicit sides without inferring allegiance. During compatibility, it adapts valid legacy hazard and global field-effect rows to reserved deterministic IDs. A native zone with the same reserved ID or logical global-field kind/ID shadows the adapter record, so lazy migration cannot apply one rule twice; free-form hazard owner labels are never promoted to side identity, and legacy area terrain without cells fails closed.

Sunny and Rainy calculations consume that active zone query rather than trusting the renderer/editor arrays. Sunny Fire/Water and Rainy Water/Fire changes enter the ordered pre-type damage pipeline as separate field-source modifiers with stable reason codes; an immune recipient prevents the weather contribution rather than turning immunity into minimum damage. The same server query supplies Hurricane/Thunder's Sunny AC 11 and Rainy cannot-miss rules, canonical solar-healing percentages, and Solar Beam/Solar Blade charge and Rainy DB-6 decisions. If Sunny and Rainy coexist, cannot-miss has explicit precedence for those accuracy checks, while exclusive healing/charge rules fail closed until a reviewed conflict choice exists. Suppressed native weather shadows its legacy presentation row but contributes none of these mechanics.

Encounter history is authoritative typed state, not a combat-log parser. Bounded per-placement indexes retain the last declared and completed move, last damaging move received, acted flags, and consecutive-use count. Turn and round windows aggregate actual HP and temporary-HP loss by move resolution, source placement, and recipient; scene windows retain switch/recall/send-out and KO facts plus move-resolution parent/child IDs. Turn-start and round-start facts reset only their matching windows, while switch/KO facts reset affected consecutive-use chains and scene boundaries clear all scene-local history. Move-rule contexts expose immutable queries over these records for the closed move-history expression set and detailed turn/round damage or ancestry queries. Scene-end handlers observe the outgoing history before it is cleared.

Encounter action resources are also authoritative typed state. Bounded placement ledgers model Standard, Shift, Swift, Free, Full, Interrupt, and Reaction action budgets/spends, reaction availability, movement budget/spend, once-per-turn flags, and typed Set-Up/Execute state. Each value declares its lifecycle reset boundaries; round/turn/recall/send-out/KO/scene facts reduce them through the same pure lifecycle boundary, and immutable move-rule contexts expose fail-closed resource queries. Native MoveSpecs consume strict reviewed phase declarations; retained v1 and pre-cost v2 definitions pass through a closed server-only range adapter. Immediate move effects and costs share one map/sheet transaction. A suspended move commits only costs through its current phase, retains cumulative declaration compensation, and resumes strictly after the last committed phase. Deferred Exhaust/Priority prerequisites use the durable pre-resolution ledger while due availability checks use current resources, so earlier spends from the same saga are neither mistaken for prior actions nor paid again. Full/Standard/Shift coupling, shared Interrupt/Reaction availability, movement budgets, once-per-turn flags, Exhaust, Set-Up/Execute, and Priority all fail before durable mutation when unavailable. Exact declaration or response replay returns the stored outcome without planning or spending again.

A forward live-play initiative command emits `turn-end`, then `round-end`/`round-start` when wrapping, then `turn-start`; beginning an inactive round emits its start before the first turn. The same reducer decrements fixed global fields only at their declared round boundary, activates a delayed Room once at round start, and expires scene-duration fields at scene end. Native field state and its compatibility renderer lane commit with initiative, so duplicate command delivery cannot tick or expire a field twice. Manual `tickFieldEffectDurations` remains a typed, GM-only correction and is labeled as such; it never replaces normal initiative advancement. Scene changes emit `scene-end` before `scene-start` when replacing an active scene. Scene-end triggers observe the outgoing scene and its temporary HP before cleanup, while scene-start triggers observe the newly active scene after old scene resources have cleared. Scene-duration effects expire, suppression references are reconciled, bounded encounter history and reserved scene counters/resources and pending summaries reset, and map move usage, temporary HP, combat logs, legacy Order effects, start-turn state, and assisted opportunity prompts do not leak into the next scene.

The same accepted-result transaction persists boundary effect expiry, currently reducible due direct-HP/heal/condition/stage operations, map state, every changed sheet, the terminal operation result, and authorized realtime rows after validating all calculated-order and mechanics sheet revisions. Unsupported triggered operations fail the command before mutation. Duplicate `opId` delivery cannot tick or apply a boundary batch twice, and initiative/scene patches carry the resulting encounter and temporary-HP state for connected clients. `previousInitiative` and administrative `setInitiative` do not replay forward lifecycle facts. A complete GM-authored manual order bypasses calculated initiative queries; otherwise active typed initiative modifiers are queried over the calculated score without rewriting placement initiative. Concrete move/field trigger registrations remain deferred to their owning tickets.

Persistent canonical conditions remain sheet-owned. Authoritative placed-token snapshots use one pure effective-condition query to combine normalized sheet strings with active typed condition effects that address the placement, its explicit side, or its occupied cells. The projection deduplicates ordinary names, preserves intentional stacks, applies active suppression without rewriting either layer, and retains applicable effect source, duration, charge, stack, and payload data for typed rules. Persistent condition reducers independently seed from the backing sheet rather than the projected token, preventing timed or source-linked encounter state from being flattened into a sheet update.

Reducer output enters an immutable typed state-change plan rather than an arbitrary JSON patch. The plan retains one global operation order while grouping changes by map, encounter state, placement, sheet, and separately revisioned external resource. Each physical resource has one expected revision, and exact aggregate before/current values carry either a reviewed restore-previous-value compensation candidate or an explicit reason why compensation is unavailable. On acceptance, the server projects those candidates into private, strictly typed correction metadata stored beside the terminal operation: each entry names its stable inverse-operation ID, source/state-change identity, exact owning resource revisions, expected current value, and restore value. Sheet plans are reduced to owned HP, condition, combat-stage, or move-usage values rather than retaining a generic sheet document. Encounter plans are split by typed container; effects/resources may be reversible while accepted history and terminal pending-summary transitions remain explicitly unavailable. Unavailable work is classified as irreversible or externally observed. This private metadata is not included in HTTP results, accepted patches, realtime events, replay, or player-visible traces.

`POST /api/maps/move-corrections/apply` is GM-only, requires **Run Live Play**, and accepts a strict mechanics-free command containing the correction `opId`, map/base revision, accepted origin `opId`, and selected inverse-operation IDs. The server resolves selections only from the source row's private metadata, canonicalizes source order, re-reads all affected resources, and checks each recorded post-move revision and typed expected-current value. It then applies the selected map and sheet inverses, advances one map audit revision and one revision per changed sheet, stores the terminal correction with indexed source ancestry, and appends authorized sheet plus `move.correction` accepted realtime rows in one SQLite transaction. The public correction patch carries source/correction IDs, selected operation IDs, resource revision transitions, map-visible lane changes, and sheet references—never inverse values or private sheet documents. It does not invoke the original resolver or RNG. Any later affected-resource revision or value drift produces a terminal conflict with no map/sheet overwrite or accepted realtime event; exact duplicate correction `opId` delivery returns the original terminal result without applying again.

Accepted automated move-log entries retain their causal live-play operation ID. Only a GM receives the **Operation details** control. `GET /api/maps/move-corrections/details?slug=<map>&originOperationId=<op>` is GM-only and projects the private compensation row into typed effect categories, affected resource identities/revisions, explicit non-reversible warnings, and ancestry-linked accepted/conflicted correction attempts. It never returns expected-current values, restore values, inverse payloads, rolls, or source sheet documents. The correction panel sends only selected server-issued inverse IDs, distinguishes loading/pending/accepted/conflicted/error state, adopts accepted authoritative map/sheet documents, and keeps the original operation plus every terminal correction linked in its durable history. Player combat logs never render this control and the details route rejects players before reading compensation metadata.

Native v2 core-token reducers apply server-resolved damage, direct HP, healing, scene-local temporary HP, Injury automation, canonical conditions, and capped combat stages through local accumulators. Map reducers project typed usage changes, locale-independent structured log operations, durable accepted-result presentation, and native hazard/pledge zones into one map revision and the same grouped CAS envelope. A reviewed hazard operation derives cells only from a revalidated durable selection or authoritative Blast/Line geometry, applies exact/up-to and connectedness policy, and stores server-derived operation/source-placement plus explicit side IDs. Reapplication caps independent per-cell layers and charges. Typed removal can address an exact zone or a bounded family/ownership/geometry match; side swap derives both sides from authoritative actor/recipient placements and changes them atomically. Legacy `hazards[]` rows remain untouched compatibility data and their free-form owners never participate in allegiance.

Registered battlefield entry hooks now bind durable handler IDs to a closed server registry. From one complete authoritative movement path, the pure zone planner evaluates explicit source sides, grounding, type immunity/absorption, and zone layers; emits only typed direct/tick HP, condition, combat-stage, or exact removal operations; and returns a map/sheet state plan that remains separate from the placement transition for atomic command composition. Spikes, Toxic Spikes, and Sticky Web contribute Slow Terrain to the authoritative movement oracle only for eligible movers. Toxic Spikes select Poisoned versus Badly Poisoned by layer and are absorbed by grounded Poison types; Sticky Web lowers Speed and is absorbed by grounded Bug types; Spikes and Fire-style entry damage use the shared Tick operation. Every canonical hook is once-per-movement, and its trigger table is derived from the complete path rather than mutable process memory, so crossing multiple cells of one zone, resume, and replay cannot enqueue it beyond policy. Unknown allegiance fails enemy-only mechanics closed. Global-field replacement, suppression visibility, ownership, and lifecycle are centralized; Sunny/Rainy calculations use that active-field boundary, while Hail/Sandstorm, terrain, Room, and barrier calculations remain assigned to their later Phase 6 tickets. Reducers independently verify emitted recipients, retain applied/prevented/no-op outcomes in the audit trace, and never mutate the authoritative snapshot. Legacy v1 mechanics still resolve their existing flat transaction exactly once; the compatibility adapter validates its typed trace entries and projects those already-resolved outcomes into the same state-plan contract with operation provenance. It never reruns mechanics or interprets effect prose, automation notes, or log lines as rules.

Hazard placement uses server-authored durable multi-cell choices. A reviewed MoveSpec declaration binds an exact/up-to count, PTU range, adjacency and connectedness policy, placement-occupancy policy, and bounded horizontal-plane or explicit reviewed-cell geometry to one move operation; the server derives the origin from the authoritative actor. Execution stops before hazard, usage, or later-phase mutation, then suspension materialization binds canonical elevation/row/column options to the durable resolution and continuation map revision. The private pending row retains cells, operation identity, and cell-set identity, while only an authorized pending-response projection exposes selectable cells. Pending creation, its map-visible summary, and reached declaration costs commit atomically, and replaying the declaration operation restores the same window without replanning, spending, or advancing revision again.

The battlefield overlay submits only the durable resolution/window IDs and selected opaque option IDs, including a canonical empty list for a reviewed zero-minimum choice; it never submits coordinates, range, occupancy, adjacency, connectedness, geometry, or hazard operations. On resume, the server resolves those IDs from the private window and revalidates the complete exact/up-to selection against the fresh authoritative map revision, bounds, actor-derived origin, reviewed range/geometry, current placement occupancy, and adjacency/connectedness policy. Only that canonical revalidated cell set enters the native zone reducer; accepted move compatibility transactions no longer mirror it into free-form `hazards[]`. A forged, over-count, disconnected, occupied, out-of-range, or stale answer terminally conflicts without applying a zone, usage, sheet, or partial map state. The response command and final encounter-zone write share one transaction, and exact response-operation replay returns the stored terminal outcome without reducing or placing any cell again.

Relationship-dependent move rules use one centralized server query seam and only accept placement IDs; callers cannot supply side-bearing participant objects. The seam resolves self, ally, enemy, or unknown from the snapshotted placement assignments and map-local side directory, then applies self, ally, enemy, same-side, other, and unknown predicates with one stable relationship reason code. Unknown allegiance fails closed for ally/enemy and same-side mechanics: token ownership, player control, GM control, and mere map presence never imply that two placements are allies. A reviewed `allowUnknown` policy may admit an existing unaffiliated placement through broad other/unknown targeting, but it never classifies that placement as an ally or enemy and never admits a missing placement. The target-predicate kernel derives self, other, ally, enemy, same-side, or any legal sets from server-authored candidates before intersecting requested IDs; it restores authoritative ordering, excludes duplicate requests and the actor when declared, and requires server-owned willing/unwilling evidence when the reviewed rule calls for it. Its pre-mechanics state gate reads immutable authoritative target facts for conscious/fainted and grounded/airborne state, scene switch history, turn/round action and damage history, effective conditions, types, keyword-immunity tags, canonical size and Weight Class, sheet kind, and held/equipped item IDs. State clauses are bounded, typed all-of declarations with explicit set matching; missing target facts fail closed, and consulting them records the backing sheet in the resolution read set before any later roll or effect. Placement `sideId` values and their map-local side directory are persisted through revision-checked GM setup saves; Prepare Map controls are the only browser mutation surface for creating, renaming, archiving, or assigning them.

Line of sight and cover use one immutable server query over snapshotted voxel and placed-token geometry; no client visibility flag participates. Rays are evaluated between the complete source and target footprint volumes, so any visible target cell permits targeting while the result still distinguishes full and partial visibility. A voxel is Blocking Terrain only when its explicit `blocksSight` override or reviewed material default says so. Ordinary intervening combatants and voxels explicitly tagged `rough`, `rough-terrain`, or `cover` count as PTU Rough Terrain and apply one non-stacking -2 Accuracy modifier on the least-covered legal ray; a server-projected combatant may instead be marked as Blocking Terrain by typed authoritative state. Reviewed server mechanics such as Groundsource can select the explicit ignore-blocking/ignore-rough policy, but browser intent cannot. Every source, target, or intervening footprint that materially participates is added to the sheet read set.

The pure server movement oracle is the authority for normal live-play token movement and move-driven Pass movement. From a map-local placement ID plus authoritative map and sheet snapshots, it resolves the footprint, available and actually used Movement Capabilities, PTU diagonal/slow-terrain cost, endpoint occupancy, terrain evidence, complete sheet read set, and ordered footprint leave/enter steps. Each step also records, in authoritative map order, exactly which other footprints were adjacent at its origin but not its endpoint. Equal-cost ordinary routes use stable direction and queue ordering. The ordinary `moveToken` command sends only its requested endpoint as mechanics intent: the legacy browser `pathLength` hint may remain in exact outbox bodies but is ignored for legality and logs, and out-of-bounds endpoints reject instead of being clamped. Before map CAS, every consulted sheet revision is revalidated inside the accepted-result transaction. Standard movement atomically spends its Shift action and exact oracle-derived distance against the oracle-derived capability budget; an unavailable action or remaining distance rejects without moving or recording a success. Its accepted `token.position` patch carries the validated previous/current turn-resource lane so realtime peers adopt the same spend. An authenticated GM may explicitly request `movementPolicy: "gm-override"` to use the reviewed no-cost exception and replace only that speed ceiling with the bounded server override; terrain capabilities, route geometry, occupancy, collision, and bounds still fail closed. The map UI uses this policy only when a GM deliberately confirms a geometrically valid but ordinarily unreachable preview.

One immutable movement projection now combines authoritative sheet capabilities with active placement-, side-, or cell-scoped typed effects. It models Overland, Sky, Swim, Burrow, Levitate, Phasing, Jump, and Wallclimber-derived Climb; Phasing removes Slow Terrain's extra movement cost and Climb validates elevated routes against adjacent blocking terrain. Jump retains separate Long/High limits for reviewed destination queries. Capability grants may carry a bounded integer value, suppressions remove only the effective mode, and ordered numeric `movement` modifiers apply without rewriting the sheet. Effect expiry/removal therefore restores the sheet projection on the next query. Grounded/airborne and typed semi-invulnerable state are separate mechanics fields: neither map elevation nor sprite/display height can create either state.

Dig, Dive, Fly, Bounce, Sky Drop, Phantom Force, and Shadow Force setup states use reviewed scene-duration capability-effect groups. A normal setup has one user effect; Sky Drop atomically links one airborne user effect to one carried-target effect by authoritative source operation. While active, ordinary move declarations and token movement fail closed, carried targets cannot act, and target selection excludes the participant unless the attacking move and reaction timing match the reviewed exception table. Exception evidence carries mechanics such as Gust/Twister range and Damage Base overrides, Hurricane automatic accuracy, underground Earthquake/Magnitude access, and Sky Uppercut setup cancellation; the browser cannot declare an exception. Resolution obtains only a server-owned destination option, validates traversal through the movement oracle or capability-ignoring appearance endpoint policy, checks required target adjacency, and moves a carried pair with preserved separation before returning exact linked cleanup events. KO, recall, switch, explicit cancellation, one-sided linked-effect removal, and scene end clear every participant effect deterministically, so refresh or interruption cannot leave a token vanished or a target carried. These definitions are engine machinery only; Phase 9 owns production move registration and semantic promotion.

For a reviewed Pass template, the client submits only the selected direction. The move resolver supplies that direction and the reviewed distance bound to the same oracle, which keeps the path straight, treats crossed placements as traversable, derives the farthest capability- and terrain-legal empty endpoint, and records every consulted occupancy sheet. The accepted Pass attack cells retain the reviewed area geometry up to the oracle-selected endpoint, while facing, durable movement, distance spend, and movement budget come from that same result; preview destinations and paths remain presentation hints. Pass movement never uses the GM override.

A pure movement-lifecycle runner materializes every oracle path as one deterministic causal event chain. Within each step it emits lost-adjacency facts first, then vacated footprint cells, entered footprint cells, and finally a committed-step marker whose last instance is the final-destination fact. Forced displacement carries the same step evidence; teleport, swap, and appearance transitions carry one endpoint-only step with no lost-adjacency or opportunity-attack implication. A lifecycle handler may enqueue only a typed `movement-step` reaction request at a movement checkpoint. Lost-adjacency checkpoints suspend before the provoking step; a placement-moving checkpoint suspends after that step commits. The runner returns a path-hash-bound cursor after the exact triggering fact. Resume begins at the cursor rather than replaying prior hazards or response triggers; cancellation discards the remaining path at the last committed position. This seam is pure and does not itself persist a prompt or mutate a map. Zone handlers and durable pre-step Attack of Opportunity orchestration remain owned by MA-136 and MA-146 respectively.

A reviewed native movement request may instead declare a durable destination or direction choice. The server bounds the candidate scan and option count, runs every candidate through the same movement oracle, persists stable option IDs with typed private selection metadata, and exposes that metadata only in the authorized response view. Duplicate server candidate cells collapse before elevation/row/column ordering, while direction results use the canonical compass/vertical order; neither caller iteration order nor duplicates can change option identity or order. A direction resolves to the farthest legal endpoint on its reviewed ray; a destination is legal only when its complete footprint, movement mode, route, cost, terrain, and occupancy pass. Opening the durable window records the option set and public summary without moving the placement. Resume regenerates the option set from the current authoritative map/sheets and accepts only the selected stored ID; stale range, bounds, occupancy, capabilities, or an ID/selection mismatch terminally conflict before any movement, usage, or move effect applies. The final shift, facing, exact path, movement spend, move effects, operation result, pending terminal state, and realtime record share the resumed atomic plan. Response commands cannot carry coordinates, paths, distances, directions, or movement modes.

A reviewed `switch-request` similarly suspends before ordinary attack effects commit and offers only server-derived replacements from the current team of the actor's unambiguous on-map trainer. Already active, fainted, missing, blocked, or footprint-incompatible Pokémon are excluded; the trainer roster and every candidate sheet consulted enter the durable revisioned read set. The response submits only its issued option ID. Resume reloads that exact read set and regenerates legality before one map/sheet transaction applies the deferred damage/effects, recalls the source, and sends out the selected Pokémon. The replacement receives a distinct deterministic placement ID while inheriting the recalled position, explicit side, facing, initiative score, active initiative slot, and manual-order slot. Switch specs explicitly choose ordinary or Baton Pass state behavior; durable effects independently declare retain, expire, or Baton Pass transfer policy. A Baton Pass switch clears the source's Combat Stages, adds them within stage caps to the replacement, and rebinds each passable effect ID in place, while non-passable source state expires before ordinary source-leave cleanup. This partition prevents cleanup from deleting a transferred instance or creating a duplicate. The same plan clears source temporary HP, emits the authoritative switch lifecycle fact for history/resource and linked semi-invulnerable cleanup, removes the pending summary, stores the terminal result, and publishes realtime state. A mandatory request with no legal choice, a forged option, or any stale roster/candidate/map value commits neither the attack nor either placement.

Reviewed spatial operations describe straight forced or voluntary displacement separately from their explicit opportunity-attack policy and declare either `up-to-distance` or `full-distance-required`. A pure server reducer derives away/toward rays from complete footprints, fixed cardinal rays from reviewed data, and chosen rays only from a server-owned durable direction lookup. Distances may use the bounded expression language, including authoritative Weight Class, with reviewed rounding and bounds. Every ray step then passes through the authoritative movement oracle and retains the same ordered lifecycle-step evidence as ordinary movement: map bounds, complete placement footprints, Blocking Terrain voxels, unsupported height transitions, and unavailable terrain movement modes are checked from the current server snapshot. Reviewed displacement is not capped by the recipient's ordinary movement speed, but it cannot invent a missing Swim, aerial, Burrow, or other traversal mode. An up-to operation stops before the first illegal step and records the exact shortening reason and obstruction; a full-distance operation rejects without yielding a partial movement. Ordered recipients reserve their accepted destinations in a local immutable planning accumulator, preventing one reduction from producing overlapping endpoints.

Teleport and position-swap modes use the same pure spatial boundary without treating their endpoints as a traversed path. A teleport can move only the authoritative actor, obtains its coordinate from a server-owned destination-set resolver, enforces reviewed range, complete source/destination footprints, Blocking Terrain, occupancy, and the Teleporter surface rule; an aerial endpoint requires current Sky or height-valid Levitate capability. A position swap requires exactly the actor plus one explicit-side ally and server-owned `willing` evidence. It validates both current footprints, installs both proposed anchors in one candidate snapshot, and then validates bounds, terrain compatibility, third-party occupancy, and mutual overlap for both final footprints before exposing either transition. Thus a second-footprint failure yields no first movement. Relocations explicitly mark placement-leaving, placement-entering, and placement-moving lifecycle work, exact left/entered footprint cells, one endpoint-only triggering step, no intermediate traversal, and no opportunity-attack trigger. These collision-checked displacement and relocation results remain server-only planning data and do not become client-visible or committable placement patches until a persistence integration owns them.

Authoritative area resolution always completes Burst, Cone, Line, Close/Ranged Blast, Pass, or Cardinally Adjacent geometry first, in map order, and only then evaluates the reviewed MoveSpec relation/state predicate once per affected placement. Friendly intent can narrow that result but cannot add an out-of-area or predicate-illegal recipient. Complete inclusion/exclusion identities and reason codes remain in the server audit trace. Accepted move records omit rule-excluded identities and public trace summaries remove excluded target events before counting, truncating, and resequencing them. An initiating authorized HTTP response may retain its own validated Friendly exclusions, and GMs may receive them, but map-wide player realtime observer projections remove those requester-only IDs. Legacy logs state only the general fail-closed ally policy and never confirm, count, name, or explain individual exclusions; a shared observer therefore cannot discover a rule-filtered or hidden token from move results, realtime patches, trace summaries, or logs.

Current legacy ally-area declarations route through that same area-target kernel. Howl, Aromatic Mist, and Coaching apply target effects only to distinct placements on the acting placement's explicit side; enemy and unaffiliated candidates are excluded before mechanics, and unknown allegiance emits an assisted diagnostic directing the GM to Prepare Map side setup. Their self-recipient effects remain independent of area filtering. Cross-token Sweet Veil protection likewise requires a distinct in-range provider that the authoritative relationship query classifies as the target's ally, so enemy and unknown-side aura tokens never grant Sleep immunity.

### Move automation status in selection

The move menu derives automation status from the reviewed semantic manifest, not from browser-supplied sheet data or mere legacy-registry presence. `complete` moves use the normal affordance; `assisted` moves remain usable but show their structured capability blockers, limitations, and manual steps before selection; `blocked` moves stay visible but disabled with a capability summary. Interaction coverage is displayed separately because base-move completeness does not imply every ability, item, or feature interaction is covered.

This display is not an authority grant. The authoritative resolver loads its own repository status and runtime, rejects a canonical `blocked` row even if a legacy script is present, and still validates move ownership, conditions, usage, targets, and revisions. Changing client memory or markup therefore cannot promote or execute a blocked canonical move.

### Assisted reaction follow-ups

Spite, Cute Charm, Poison Point, Moxie, and Celebrate now open server-created durable cleanup windows after the provoking move commits. Eligibility is derived from the authoritative pre-move snapshot, response ownership belongs to the triggering placement (or the actor for Moxie/Celebrate), and simultaneous windows are exposed one at a time in reviewed priority order. The accepted move and its synthetic follow-up pending row commit atomically, but use distinct operation identities so the pending row never masquerades as the accepted terminal command. Refresh/reconnect reloads the authorized current window; exact response retries reuse the same response operation. Selecting an option resolves only registered server-authored condition, combat-stage, or structured-log operations, while pass closes that window without an effect. These flows remain semantically assisted because they are post-commit follow-ups rather than canonical interrupts; Celebrate retains its current typed reminder rather than moving the token.

Attack-of-opportunity responses are now server-created durable reaction windows. The provoking token's controller submits only the movement or ranged-attack trigger fact; the server derives eligible adjacent defenders, once-per-round availability, player-character suppression, and currently usable Struggle variants, then persists stable response IDs and defender-placement ownership. Refresh/reconnect reloads only windows controlled by the selected defender profile (or an authorized GM), exact trigger/response retries do not create another window or attack, and a selected Struggle resolves as a server-owned child move with causal ancestry before the defender's round usage is marked. Movement-triggered rows retain a strictly parsed durable origin/destination context, with the destination checked against the authoritative placement, so the post-action child validates its attack from the provoking origin without moving the already-committed token back. This remains semantically assisted: the current trigger opens after the provoking action has committed, so movement is not yet interrupted at the provoking step; MA-146 owns that timing correction. Registry presence or an `Auto`-style mechanics helper must not be treated as a semantic-completeness claim.

Map live-play idempotency records are keyed by map and `opId`; shop checkout idempotency records are keyed by shop and `opId`. A retry with the same command body returns the stored result without applying effects twice. Reusing an `opId` with different material is rejected.

### Live-play batch commands are not client-side macros

Sprint 4 batch commands (`clearHazards`, `clearFieldEffects`, `editTerrainVoxels`, and `editHazards`) are explicit live-play command types, not browser-side loops over primitive commands. When the UI presents one cleanup or brush intention, the client sends one bounded command body and one `opId` whenever the stroke fits within the shared batch limit. The server validates the whole payload, role/profile authority, map visibility, bounds, base revision, conflict scopes, and operation identity before mutating anything.

Accepted batch commands commit all effects, the terminal operation result, and durable realtime rows in one SQLite transaction. A rejected stale, conflicting, hidden, unauthorized, invalid, oversized, or contradictory batch applies none of its requested changes. Retry/status recovery must reuse the exact same command body and `opId`; duplicate HTTP/SSE/status terminals may acknowledge recovery state but must not apply accepted patches twice.

Shared payload bounds keep batch authority narrow: explicit hazard-cell batches are capped at 128 operations, explicit terrain voxel/cell batches at 256 operations, explicit field-effect kind operations at 16, and affected-token summary lists at 64 IDs. Strict parsing rejects unknown durable-state fields, private/profile data, arbitrary records, and over-large strings before executor code runs. Duplicate or contradictory terrain/hazard cell operations reject, except idempotent clear-by-cell payloads may normalize repeated cells.

If a live-play brush stroke exceeds its command limit, the client may split it into ordered bounded batch commands. Each chunk is still a separate authoritative transaction with its own command body and recovery state; later chunks stop after a rejected or uncertain chunk. The client must not keep terrain or hazard edits as authoritative local state without accepted patches or reconciliation.

Batch pending and recovery UI may summarize command kind and counts, for example “Clearing 12 hazards…” or “Applying terrain brush (8 cells)”, but it must not display full payload coordinates, raw command bodies, profile IDs, sheet data, access-gate data, hostnames, or secrets. Presence, pings, targeting intent, and GM attention remain presentation-only and never transport batch commands.

## Durable realtime events and authorised SSE replay

Persistent map, sheet, shop, group inventory, library, folder, and mode mutations append durable realtime events in the same SQLite transaction as their authoritative writes. Each row carries an explicit server-internal access descriptor: `gm-only`, `map-access`, `sheet-access`, `group-inventory-access`, `shop-access`, or `pending-move-response-access`. Delivery evaluates that descriptor against current SQLite state and the connection principal; it does not trust channel names or payload fields. The pending-response descriptor rechecks the current map, durable resolution/window, selected profile token control, and ownership before any private option event can be delivered.

The normal live-play stream is `GET /api/events` using Server-Sent Events. The stream keeps quiet tables open with heartbeat comments and records SSE connect/disconnect events for operator diagnostics. A reconnect is a possible missed-event gap, so clients reconcile from `/api/maps/load?slug=<slug>` when replay cannot bridge the cursor. Replay rows have one globally monotonic sequence. Initial connections without a cursor start at the current tail and do not replay stale history. Reconnects send a per-context `after` cursor and receive only authorised retained rows. Denied rows are never serialized to the client; they still advance checkpoints so clients do not loop on inaccessible events.

Access boundaries:

- hidden maps never reach players;
- a profile receives only its own profile-linked sheets plus public/player-visible map sheets;
- unprofiled player context has its own cursor and sheet-access rules;
- GM-only folders, tombstones, and administrative library events never reach players;
- shop updates reach players only while the referenced shop is currently open and player-visible;
- private pending-response events reach only the current window's eligible profile/controller or an authorized GM;
- denied pending-response rows advance replay checkpoints without serializing their payload or access metadata;
- profile changes close the old stream before opening the new profiled stream.

The server combines in-process wakeups with SQLite polling, so one process can commit a durable event and another process can deliver it after polling or restart. Wakeups and polling share the same sequence cursor and do not duplicate delivery.

Shopfront and GM shop editor pages subscribe to `shop:<slug>` for the loaded shop document. Shop checkout commits also append terminal `live-play-command-accepted`/`live-play-command-rejected` rows on `shop:<slug>` so the originating checkout outbox can be acknowledged even when SSE wins the race with the HTTP response. Accepted terminal shop events carry the authoritative shop document only; trainer sheet and group inventory convergence still uses their resource-specific channels or an explicit reload, so shop-access replay does not expose participant documents to every shop viewer. Shopfront checkout state also subscribes to `group-inventory:<slug>` and `sheet:trainer:<slug>` only for payment/delivery documents already loaded on the page. Client handlers ignore ordinary local echo document events by `clientId`, reject stale revisions, and apply only complete authoritative documents. When another client changes finite stock below a cart quantity, the cart clamps to the new limit and shows a non-blocking stock-change notice instead of sending an optimistic or stale checkout.

## Ephemeral presence and table-feel state

Live-play presence is presentation-only table-feel state, not gameplay authority. Connected participant summaries, remote token hover/selection, map pings, targeting or measurement intent, and GM attention requests are short-lived signals that help players coordinate around the map. They never grant token control, never satisfy command authorization, never mutate map/sheet/shop/group-inventory documents, never advance map revisions, and never replace explicit live-play command routes.

Presence uses the map presence snapshot/heartbeat API plus transient `/api/events` delivery when available. Presence entries are sanitized to display-safe participant labels, roles, tab suffixes, accents, visible token IDs, small intent summaries, short ping labels, and optional GM attention targets. The presence contract rejects command bodies, sheet payloads, raw profile IDs, access-gate data, hostnames, secrets, arbitrary records, over-large strings, durable-state fields, and hidden/private details.

Server-side presence is process-local in memory and expires by TTL. It is not written to SQLite, campaign JSON, the durable realtime event log, cursor storage, outbox journals, or operation-history tables. Transient presence updates are unsequenced and non-durable; reconnecting clients rebuild table-feel state from the current snapshot and fresh heartbeats, not from replay history. A service restart or process handoff may clear presence without affecting authoritative gameplay state.

Presence access follows the same role, selected-profile, and map visibility boundaries as live-play viewing. Hidden maps do not expose presence, pings, remote attention, or intent to players. Profile changes close the old realtime context and clear old-context presence before the new profile publishes fresh display-safe state. Client-published token IDs, ping cells, intent cells, and GM attention targets are dropped or rejected unless they are visible in the caller's current map context; player-authored GM attention requests are rejected or downgraded to ordinary table pings.

Presence failure must degrade gracefully. Snapshot failure, heartbeat failure, lost transient updates, stale entries, hidden-tab throttling, or missing presence freshness metrics may show a small non-blocking status, but command dispatch remains governed only by the existing command, outbox, replay, reconciliation, revision, and authorization blockers. Local predictions, pending indicators, correction notices, and authoritative patches keep priority over remote hover/selection/intent overlays.

## Retention and gap reconciliation

The durable realtime log is replay history, not permanent campaign state. Retention can prune old rows by age and row count while preserving cursor-state invariants. A pruned cursor produces a controlled `gap` response; a cursor beyond the latest sequence produces an `ahead` response. The client treats either as a single aggregate snapshot requirement, reloads authoritative SQLite map/sheet/mode state, advances the context cursor to the server tail, and never rewinds a stored cursor.

Retention is configured by environment variables and can be inspected or run manually with the operator scripts:

```sh
npm run realtime:status
npm run realtime:prune
```

The scheduler uses the same repository pruning path as the CLI and must not mutate client cursor storage; clients reconcile from server cursor state on their next stream.

## Client cursor and recovery model

Realtime cursors are stored per delivery context: GM, unprofiled player, and each selected player profile. Reconnect/replay pauses live-play command dispatch until the client is caught up or reconciled. The map page state machine exposes loading, ready, saving-command, reconnecting, reconciling, stale, and error states.

Local predictions are presentation-only overlays on top of the last authoritative map. The narrow predicted surface is token movement/facing plus token-level pending feedback for supported simple HP or condition edits; it does not mutate cached sheet documents or become durable state. When a remote authoritative patch arrives while local predictions are pending, clients adopt the authoritative patch against clean map state and then layer back only safe non-conflicting predictions. Conflicting predictions roll back through correction or reconciliation. HTTP, SSE, replay, and status-check terminal results for the same `opId` are idempotent: stale duplicates can acknowledge recovery state but must not apply patches twice or roll back already accepted state.

The originating map view highlights tokens that are waiting for server confirmation, keeps unrelated tokens interactive, and shows a small correction notice if the server rejects a predicted token action and the overlay rolls back.

The recovery panel means:

- **Pending/queued**: command is journaled locally before send and has not reached a terminal state.
- **Sending**: a lease-owning tab is sending the exact journaled body.
- **Uncertain**: the HTTP response was lost; retry/status must reuse the exact same `opId` and body.
- **Accepted/acknowledged**: accepted SSE or terminal status removed the outbox row.
- **Abandoned**: abandonment serialized against execution and no future retry should send the command.

Recovery never replays local presentation-only effects. Duplicate accepted/status results are idempotent and do not apply state twice.

## Outbox, status, retry, and abandonment

Map live-play commands and shop checkout commands can be journaled in IndexedDB before send. The journal stores request path, exact body, auth context, fingerprint, state, attempts, and lease data; shop checkout rows are scoped by `shopSlug` and do not require a top-level `mapSlug` for shop-page-origin purchases. Retry resends the exact body and `opId`. Map command status checks are read-only. Map abandonment serializes against execution; if the server has already accepted the command, the accepted result wins and acknowledges the outbox. Accepted SSE acknowledges matching map outbox entries; shop checkout terminal SSE acknowledges matching checkout outbox entries and stale local shop state requests reload/reconciliation instead of applying an out-of-date result over newer local state.

## JSON import/export boundary

Use JSON only for explicit maintenance:

- Operators can migrate an existing private campaign with `npm run migrate:sqlite`; the command imports maps/sheets/folders into SQLite, creates a pre-migration backup, validates rows, and validates that imported maps/sheets can be loaded from the database.
- `npm run export:sqlite-json -- --output /safe/export/path` exports SQLite maps/sheets/trainers, group inventories, and shop tables for backup or interchange. Use `--force` only to replace a known export destination.
- Standalone encounter generation may emit JSON as explicit generation output; encounter spawn does not use generated JSON as runtime authority.

Do not treat residual JSON under campaign roots as fallback state. Do not commit private campaign JSON or generated runtime artifacts.

## Operator runbook

Required/private-host environment variables:

- `ROTOM_CAMPAIGN_ROOT`: private campaign directory. Keep it outside the app repository for production-like hosts.
- `ROTOM_DB_PATH`: optional SQLite database path. Defaults to `rotom-table.sqlite` under `ROTOM_CAMPAIGN_ROOT`.
- `ROTOM_ENABLE_HOSTED_WRITES=1`: exact production opt-in for hosted writes. Production without this flag fails closed for covered writes.
- Realtime retention variables from `server/realtime/realtimeEventRetentionConfig.ts`: enablement, retention days, max rows, and prune interval.

Backup expectations:

1. Stop the service when possible, or pause table activity and use SQLite's backup API.
2. Back up the database plus WAL sidecars: `rotom-table.sqlite`, `rotom-table.sqlite-wal`, and `rotom-table.sqlite-shm` when present.
3. Include residual maintenance JSON such as player profiles, encounter tables, reference overrides, assets, and any intentional import/export copies.
4. Store archives outside the tracked app repository and verify a restore before relying on them.

Retention operations:

```sh
npm run realtime:status        # inspect current cursor/log/retention plan
npm run realtime:prune         # apply configured prune policy once
```

Diagnosing replay gaps:

- A `gap` means the client's cursor is older than retained history. Reload the aggregate snapshot and continue from the reported latest sequence.
- An `ahead` means the client cursor is newer than the server tail, usually after restore or rollback. Reload the aggregate snapshot and reset only through the normal client reconciliation path.
- Repeated gaps usually mean retention is shorter than the supported reconnect/recovery window.

Safe rollback/restore:

- Restore SQLite database and WAL sidecars as one unit.
- Expect clients with cursors from the abandoned future to receive `ahead` and reconcile from a snapshot.
- Do not copy JSON maps/sheets/group inventories over SQLite as a rollback mechanism; import/export is an explicit maintenance operation.
