# Rotom Table 1.0.1 release notes

> **Released locally:** Rotom Table 1.0.1 is the owner-authorized deterministic successor to the immutable, unpublished `v1.0.0` tag. Remote publication, deployment, artifact upload, and evidence upload remain unauthorized.

Rotom Table 1.0.1 contains the same core-complete trusted-table liveplay product and storage schema v56 as 1.0.0. This patch changes release-build determinism and verification tooling only; it does not change gameplay mechanics, canonical PTU data, campaign storage semantics, or the accepted licensing boundary.

## Operator release notes

### Why this patch exists

Repeated supported-shape builds of `v1.0.0` produced different SHA-256 manifests even though runtime identity and functional checks passed. The tag remains immutable and unpublished, and it must not be represented as verified. The failed attempts and root cause remain recorded in the [released-identity verification](../../data/release-readiness/released-identity-verification.v1.json).

### Deterministic build repair

Release builds now:

- derive Nuxt's release-only build ID from package and commit identity;
- use stable linked client CSS instead of asynchronously grouped SSR style chunks;
- sort Nitro's embedded public-asset metadata by path;
- normalize Nitro build dates and asset mtimes to `SOURCE_DATE_EPOCH`;
- install the exact checked-in lock through `npm ci --include=dev` inside `npm run release:prepare`;
- fail closed if the expected generated metadata cannot be normalized.

Exact checksum comparison remains mandatory. A mismatch requires another patch and never permits moving an existing tag or weakening the comparison.

### Release identity

The package, lock, `/api/health`, `/api/version`, and **Settings → About Rotom Table** report version `1.0.1` and storage schema v56. The supported builder remains Linux x86-64, Node 24, and npm 11 with commit/tag provenance.

### Deployment and campaign data

The supported deployment remains one private Linux x86-64 VPS per campaign group, behind an outer access gate, with the built Nitro server managed by systemd and bound to loopback. Production campaign writes still require exactly `ROTOM_ENABLE_HOSTED_WRITES=1`.

No database migration is introduced. Existing schema-v56 campaign databases remain schema v56. The same [upgrade guide](../release/upgrade.md), [backup/restore runbook](../private-vps-backups.md), [hosting runbook](../private-vps-hosting.md), and exact pre-upgrade-backup rollback boundary continue to apply. Database downgrade remains unsupported.

### Verification and publication boundary

The local release transaction created immutable annotated `v1.0.1` at commit `3dd60fd843af50b3efc40735cc2bf8bb8e8652b4`. Its status-zero `release-evidence/` reference and a second clean exact-lock build each produced 12,663 files/377,746,951 bytes, zero artifact-audit findings, and checksum manifest SHA-256 `82fb0dfd…`; the second build reproduces every output checksum with zero differing paths.

The owner authorized one local `1.0.1` transaction only. This does not authorize pushing tags, publishing notes, uploading artifacts or evidence, deploying a host, or claiming legal clearance. The explicit 1,460-file recommendation-5 Trainer-profile residual risk and `legalClearanceClaimed: false` remain unchanged.

For the complete GM/player capability guide and six frozen product limitations, read the historical [1.0.0 product notes](1.0.0.md). The verification hold at the top of those notes applies to `v1.0.0`, not to any claim that its tag was changed.
