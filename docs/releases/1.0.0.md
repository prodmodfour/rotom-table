# Rotom Table 1.0 release notes

> **Released locally, verification hold:** Rotom Table 1.0.0 was minted on 2026-08-28 through the owner-approved atomic release transaction. Its immutable local annotated `v1.0.0` tag later failed exact checksum reproduction and was never published. Do not publish or deploy it as a verified release. The deterministic source repair requires a separately authorized `1.0.1` successor; remote publication remains a separate owner action. See the [failed-closed released-identity verification](../../data/release-readiness/released-identity-verification.v1.json).

Rotom Table 1.0 is the first core-complete release of the private trusted-table liveplay companion for Pokémon Tabletop United. It joins Field Guide reference, Workshop preparation, and Live Encounter play around a SQLite-authoritative campaign and a narrow private-VPS support boundary.

## Operator release notes

### Supported production shape

1.0 supports one private Linux x86-64 VPS per campaign group, Node `>=24 <25`, npm, a production Nuxt/Nitro build managed by systemd, a loopback-only origin, and an outer access gate for known table members. Desktop and mobile certification covers Chromium-family projects only. Local development remains available to contributors, but local hosting is deprecated for live campaign play.

The GM/Player picker remains a trusted-table role choice, not public authentication. Do not expose the origin or app routes to arbitrary internet users. Follow the [private VPS hosting runbook](../private-vps-hosting.md), [deployment smoke checklist](../private-vps-deployment-smoke-checklist.md), and [liveplay smoke checklist](../private-vps-live-play-smoke.md).

### Source install and service update

Build only from a clean, reviewed immutable revision. Source builds require development build tooling even when the deployment shell has `NODE_ENV=production`:

```bash
cd /srv/rotom-table/app
git status --short # must be empty
git rev-parse HEAD
git --version
node --version      # must report v24.x
npm ci --include=dev
npm run check:release-readiness:deployment
npm run typecheck
npm run build
```

For an existing host, create the release-boundary backup and stop the old service before replacing `.output/`. Do not build over a checkout still serving a session. Start the reviewed systemd unit only after the `rotom-table` service account can read the built entry point and write the configured private campaign root.

The standard environment uses:

```dotenv
NODE_ENV=production
NITRO_HOST=127.0.0.1
NITRO_PORT=3000
ROTOM_CAMPAIGN_ROOT=/srv/rotom-table/campaign
ROTOM_ENABLE_HOSTED_WRITES=1
```

The hosted-write flag must be exactly `1` and is appropriate only behind the outer access gate. It enables covered campaign persistence; it is not authentication, authorization, a migration trigger, or a backup substitute. If `ROTOM_DB_PATH` or `ROTOM_CAMPAIGN_ROOT` uses a nonstandard path, the reviewed systemd unit must allow that exact path in `ReadWritePaths`.

Evidence: [source distribution manifest](../../data/release-readiness/distribution-manifest.v1.json), [private-artifact audit](../../data/release-readiness/private-artifact-audit.v1.json), and [deployment certification](../../data/release-readiness/deployment-instruction-certification.v1.json).

### Campaign storage authority

Storage schema v56 is authoritative for maps, ordinary Pokémon and Trainer sheets, shared inventory and shops, live encounter state and operations, onboarding, breeding, Contests, settlement/continuation, and GM Campaign Toolkit state. Remaining campaign JSON is limited to profile, override, maintenance, explicit import/export, or private supporting material; it is not silent fallback authority for SQLite-backed runtime documents.

Keep the database, WAL/SHM sidecars, remaining campaign-owned files, environment files, backups, logs, and browser evidence outside the source checkout. Runtime PTU reference authority remains limited to the fourteen app-owned `data/reference/*.json` files plus `shared/ruleset/natures.ts`; `books/`, `ptu-data/`, and other documentary material are never production fallback sources.

Evidence: [canonical census](../../data/release-readiness/canonical-census.v1.json), [catalog regression certification](../../data/release-readiness/catalog-regression-certification.v1.json), and [source-tree hygiene](../release/source-tree-hygiene.md).

### Upgrade guarantee

The supported release-boundary upgrade inputs are:

- app-produced SQLite databases at contiguous schema heads v1–v56;
- documented JSON-era campaign roots through the explicit importer;
- a fresh or empty private campaign root.

Before any upgrade, stop table activity, create and verify the private backup, and resolve any active WAL/SHM state according to the runbook. Then choose exactly one documented command.

For app-produced SQLite:

```bash
cd /srv/rotom-table/app
npm run upgrade:campaign -- \
  --database /srv/rotom-table/campaign/rotom-table.sqlite \
  --backup /srv/rotom-table/backups/pre-1.0-rotom-table.sqlite
```

For a documented JSON-era campaign root:

```bash
cd /srv/rotom-table/app
ROTOM_CAMPAIGN_ROOT=/srv/rotom-table/campaign \
  npm run migrate:sqlite -- --backup-root /srv/rotom-table/backups
```

The SQLite upgrader rejects corrupt, partial, unknown, future, read-only, locked, and active-sidecar inputs before replacing authority. It creates or verifies a byte-exact pre-upgrade backup, migrates and audits a staging copy, fsyncs it, and atomically replaces the original only after success. Reruns converge. The JSON importer leaves source JSON in place and atomically installs the imported v56 database.

Read the complete [1.0 upgrade guide](../release/upgrade.md) before acting. Database downgrade is unsupported; rollback means restoring the exact pre-upgrade backup.

Evidence: [supported upgrade inputs](../../data/release-readiness/supported-upgrade-inputs.v1.json) and [upgrade certification](../../data/release-readiness/upgrade-certification.v1.json).

### Backup, restore, and recovery

Two release-boundary backup methods are supported:

- `npm run backup:campaign` online, using the SQLite backup API while WAL writes may continue;
- `npm run backup:campaign -- --stopped-service`, after the service is stopped and sidecars are safely resolved.

Both methods produce deterministic private archives with a manifest and SHA-256 bindings. Restore requires a fresh target root and verifies archive paths, content hashes, database integrity, foreign keys, storage schema, remaining campaign files, and private pending state before installation.

```bash
npm run backup:campaign -- --help
npm run restore:campaign -- --help
npm run audit:campaign -- --help
```

A release rollback is a data-and-code recovery operation: stop the service, preserve the failed root, restore the exact compatible campaign backup, return the app checkout to the matching known-good immutable release, rebuild if required, and complete health plus deployment/liveplay smoke checks. Never attempt a database downgrade in place. See the [backup and restore runbook](../private-vps-backups.md).

Evidence: [backup/restore certification](../../data/release-readiness/backup-restore-certification.v1.json) and [backup fixtures](../../data/release-readiness/backup-restore-fixtures.v1.json).

### Retired seams and changed operator behavior

- Production Pokédex no longer offers “restore from books.” Pokédex maintenance writes only the campaign-owned override diff under `ROTOM_CAMPAIGN_ROOT`; app-owned canonical JSON changes require a reviewed migration.
- Documentary books and parser trees are retained for provenance but are prohibited as runtime reference fallback.
- Runtime map, sheet, group-inventory, and shop JSON fallback is retired; JSON is explicit migration/interchange material only.
- Legacy `/sessions` lobby/socket surfaces remain guarded maintenance paths and are not the normal profile-play flow.
- Local hosting is deprecated for liveplay; use the supported production Nitro/systemd path.

Evidence: [canonical reachability](../../data/release-readiness/canonical-audit-reachability.v1.json), [documentary disposition](../../data/release-readiness/documentary-tree-disposition.v1.json), and [API mutation audit](../api-route-mutation-audit.md).

## GM release notes

### A complete preparation-to-continuation loop

The 1.0 workflow connects campaign onboarding, maps and ordinary sheets, live encounters, atomic settlement, breeding and Egg lifecycle, Contests, GM preparation, immutable Encounter Builder launch, restart, and restore. State that becomes authoritative is committed by the server and stored in the campaign database; reconnecting browsers resume from persisted revisions rather than inventing client state.

Evidence: [release golden journey](../../data/release-readiness/release-golden-journey.v1.json), [golden replay report](../../data/release-readiness/release-golden-replay-report.v1.json), and [aggregate integrity audit](../../data/release-readiness/backup-restore-certification.v1.json).

### Field Guide and Workshop

The Field Guide searches the reviewed app-owned Pokédex, Moves, Abilities, Capabilities, Edges, Features, Items, Conditions, Maneuvers, Rules, Contest, experience, and stat-ranking authorities. Workshop surfaces cover campaign policy and guided character onboarding, ordinary Pokémon and Trainer sheets, shared inventory and shops, map preparation, breeding projects and Eggs, Contest preparation, encounter tables, and session preparation.

The app does not silently repair reference data from books or parser trees. Campaign-specific Pokédex maintenance writes an explicit private override diff; changing app-owned canonical material remains a reviewed data migration.

Evidence: [complete catalog certification](../../data/release-readiness/catalog-regression-certification.v1.json), [canonical reachability](../../data/release-readiness/canonical-audit-reachability.v1.json), and [mechanics registry finality](../../data/release-readiness/mechanics-registry-finality.v1.json).

### Live Encounter direction

The role-projected encounter cockpit combines map context, initiative and turn cues, the active combatant, legal actions, Move/Ability/item execution, pending response windows, tactical inspection, revisions, and realtime recovery. Encounter Documents and the Builder remain distinct: preparation is inert until a reviewed launch commits an immutable handoff, and settlement commits rewards, captures, consequences, cleanup, and continuation atomically.

GMs remain responsible for table adjudication where PTU calls for human judgment. A reviewed non-automatable canonical row is not a hidden rule engine; the UI presents the needed context without pretending to replace the GM.

Evidence: [encounter presentation contract](../encounter-presentation-contract.md), [GM Campaign Toolkit acceptance](../../data/gm-campaign-toolkit/final-acceptance.v1.json), and [mechanics registry finality](../../data/release-readiness/mechanics-registry-finality.v1.json).

### Private generation and session preparation

Deterministic wild and NPC generation, ordinary-sheet package commit, encounter-table workflows, and session preparation are GM-private until deliberately projected through the normal Builder/live encounter boundaries. Previewing or retrying an unchanged request does not create extra authority; changed material requires a new reviewed request. Preparation notes, candidates, handouts, and decisions do not become live authority merely because they exist.

Use the [GM Campaign Toolkit guide](../gm-campaign-toolkit/gm-guide.md) for the supported flow. Do not copy private generation payloads, unrevealed participants, hidden notes, or campaign traces into issue reports or release evidence.

Evidence: [GM Campaign Toolkit final acceptance](../../data/gm-campaign-toolkit/final-acceptance.v1.json), [role-projection contract](../../data/gm-campaign-toolkit/role-projections.v1.json), and [release privacy report](../../data/release-readiness/release-privacy-report.v1.json).

### GM role expectations

The GM profile can perform covered campaign mutations, but it does not bypass revision, idempotency, consent, settlement, storage, or privacy contracts. Resolve revision conflicts from the newest server state, do not manually edit SQLite while the service is active, and treat export/backup files as private campaign material. Keep the app behind the outer gate even when everyone at the table is trusted.

Evidence: [liveplay authority](../live-play-authority.md), [complete-play-loop GM guide](../complete-play-loop-gm-guide.md), and [release privacy report](../../data/release-readiness/release-privacy-report.v1.json).

## Player release notes

### One connected campaign experience

Players can choose their trusted-table profile, complete guided onboarding, use their Trainer and Pokémon sheets, manage projected inventory and commerce workflows, join profile-linked maps and encounters, continue through rewards and captures, and participate in breeding and Contests without switching to a separate rules tool. The server preserves accepted operations across reconnect and restart.

Evidence: [release golden journey](../../data/release-readiness/release-golden-journey.v1.json), [complete-play-loop player guide](../complete-play-loop-player-guide.md), and [onboarding guide](../onboarding/guide.md).

### Role-safe live encounters

Player views receive the information and controls projected for that profile: visible map state, owned or assigned participants, legal actions, response prompts, accepted results, and table-safe history. GM-only notes, hidden generation inputs, unrevealed candidates, and private adjudication material are not part of the player contract. Choosing “Player” is still a trusted-table convenience rather than an internet security boundary; the deployment's outer gate protects the whole app.

Evidence: [role-projection contract](../../data/gm-campaign-toolkit/role-projections.v1.json), [release privacy report](../../data/release-readiness/release-privacy-report.v1.json), and [encounter workspace role contract](../adrs/015-role-projected-encounter-workspace.md).

### Character and long-term workflows

Guided onboarding separates draft work from the reviewed atomic character commit. Breeding preserves consent, project, Egg, hatch, and recovery boundaries. Contest preparation and runtime project only the participant-safe information needed for the selected format. Settlement and campaign continuation update durable sheets and inventory through server-owned operations rather than browser-owned edits.

Evidence: [onboarding final acceptance](../onboarding/final-acceptance.md), [breeding GM/player guide](../breeding/gm-and-player-guide.md), [Contest player/GM guide](../contests/player-and-gm-guide.md), and [release golden replay report](../../data/release-readiness/release-golden-replay-report.v1.json).

### Player role expectations

Use the profile assigned by the table, wait for accepted or conflict feedback before repeating a command, and refresh from server state after a revision conflict. Do not treat a disabled control or unprojected value as permission to call a GM route directly. Report a privacy leak privately and avoid including campaign names, character details, screenshots, or database files in public reports.

Evidence: [player profiles](../player-profiles.md), [liveplay authority](../live-play-authority.md), [security reporting boundary](../../SECURITY.md), and [support expectations](../support.md).

### Player-safe example

During a visible encounter, a player may select **their active Pokémon**, choose an available Move, choose **a visible target**, review the projected accuracy/effect context, and submit once. The UI then shows an accepted result, a pending response prompt, or a revision conflict to refresh. This example intentionally names no hidden target, unrevealed stat block, generation seed, GM note, or private reward.

Evidence: [action decision and resolution contract](../encounter-workspace/action-decision-resolution.md), [release privacy report](../../data/release-readiness/release-privacy-report.v1.json), and [release golden journey](../../data/release-readiness/release-golden-journey.v1.json).

## Known limitations (frozen)

The following six statements are rendered verbatim from the owner-accepted [known-limitations register](../../data/release-readiness/known-limitations.v1.json):

- The GM/Player role picker is a trusted-table convenience, not public authentication.
- Rotom Table 1.0 supports one private Linux x86-64 VPS per campaign group, behind an outer access gate.
- Browser certification covers the Playwright Desktop Chrome and Pixel 7 Chromium projects only.
- Supplement and expansion content packs are post-1.0 and require separately reviewed app-owned canonical data.

These are the only release-gate outcomes allowed to close as **Documented boundary**. Any failing core-mechanics, licensing, migration, critical-usability, or other release row not listed in the register remains a blocker until explicitly reviewed; release-note wording cannot convert it into a limitation.
